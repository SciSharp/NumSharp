# NumSharp.Tests.Interop — testing against LIVE NumPy for byte-perfect parity

This is the one test project that runs **real CPython + NumPy embedded in the test process** (via
pythonnet). Everywhere else NumPy is an *offline* oracle — a committed corpus of bytes generated by a
separate `python` run (`test/oracle/`, `test/NumSharp.Tests/**`). Here NumPy is a **live** oracle:
the test asks the source of truth to compute the answer *right now*, over NumSharp's own memory, and
asserts the two results are **byte-for-byte identical**.

That makes this the strongest parity gate in the repo. A committed corpus proves parity against a
snapshot; a live oracle proves it against the NumPy actually installed, over the exact bytes NumSharp
produced, with no serialization step in between that could hide a divergence.

> **The claim this project makes:** for an op NumSharp implements, `NumSharp.np.OP(x)` produces the
> **same bytes** as `numpy.OP(x)` where `x` is *literally the same buffer* — because we hand NumPy
> NumSharp's memory (zero-copy) and let NumPy's own kernels run over it.

---

## 1. The canonical recipe

Build the input in NumSharp, export it **zero-copy** to NumPy, compute the op in **both** stacks,
compare the results byte-for-byte:

```csharp
[TestClass]
public class MyOpLiveParityTests : InteropTestBase   // gives you Scope, Gil(), Export*/Import*, the leak gate
{
    [TestMethod]
    public void MyOp_ByteExact_VsLiveNumpy()
    {
        using var a  = np.array(new double[,] { { 4, 2, 1 }, { 2, 5, 3 }, { 1, 3, 6 } }); // NumSharp input
        using var ns = np.linalg.cholesky(a);                                             // NumSharp computes
        using (Gil())                                                                     // C-API ⇒ GIL required
        {
            using PyObject va = a.ToNumpy();                                     // ZERO-COPY export of `a`
            using PyObject np_ = Python.np.with("np.linalg.cholesky(a)", ("a", va)); // LIVE numpy over the SAME bytes
            ByteContract.AssertSameBytes(ns, np_, "cholesky lower");            // byte-for-byte
        }
    }
}
```

`np.*` is **NumSharp**; `Python.np.*` is **real numpy** (the class lives in namespace `Python`,
beside `Python.Runtime`, precisely so the two read for what they are). Never confuse them.

## 2. The moving parts

### `PythonSession` (`PythonSession.cs`) — one embedded engine per process
- `[AssemblyInitialize]` discovers a Python with numpy (`PYTHONNET_PYDLL`, then `python`/`python3`,
  then `~/.claude/python`, then Windows `Programs\Python3*`), starts the engine, imports numpy to
  fail fast, and **enables OpenBLAS as the default backend at `threads: 1`**
  (`OpenBlasEngine.TryEnable(threads: 1)`). CPython+numpy cannot re-init after `Py_Finalize`, so the
  engine lifecycle is assembly-scoped, not per-test.
- **`threads: 1` is load-bearing** — see §4.
- `EnsureOrInconclusive()` — call at the top of any engine-backed test (InteropTestBase does it for
  you). If the engine is unavailable it either **fails** (default: `NUMSHARP_PYTHONNET_REQUIRE_ENGINE`
  is TRUE — a self-skipping suite that proves nothing is worse than a red one) or reports
  **Inconclusive** (`NUMSHARP_PYTHONNET_REQUIRE_ENGINE=0`, for a dev box without Python).

### `InteropTestBase` (`InteropTestBase.cs`) — base class for engine-backed tests
- `Scope` — a `PyModule` with `import numpy as np` (+ `gc`, `array`) already run.
- Python evaluators: `PyExec(code)`, `PyLong/PyFloat/PyStr/PyBool(expr)`.
- Crossing helpers (each opens its own GIL): `ExportTo(name, nd)` (zero-copy), `ExportCopyTo`,
  `ExportMemoryViewTo`, `ImportOf(expr)` (copy numpy→NumSharp), `ViewOf(expr)` (zero-copy view).
- `Gil()` — `Py.GIL()`; open it around any block that touches a `PyObject`.
- Pointer probes `WriteAt<T>/ReadAt<T>` — prove aliasing at the byte level.
- **Leak gate:** `[TestInitialize]` snapshots `LiveExports`/`LiveImports`, `[TestCleanup]` FAILS the
  test unless they return to baseline. **Every test therefore doubles as a no-leak / no-premature-free
  assertion** — dispose every `PyObject` you make (`using`).

### `Python.np` (`Pythonic.cs`) — live numpy builders
- `eval(expr)` — evaluate a numpy expression with `np` bound (the escape hatch for layouts C# can't
  spell): `Python.np.eval("np.arange(12,dtype='<i4').reshape(3,4).T")`.
- **`with(expr, (name, val)…)`** — the workhorse: bind exported operands and let numpy's own kernels
  compute over them: `Python.np.with("np.matmul(a,b)", ("a", va), ("b", vb))`.
- `evalStmts(setup, resultVar)`, `truthy(expr, …)`, `arange/array/zeros/scalar/asarray`,
  `array_equal`, `shares_memory`. The returned `PyObject` outlives the throwaway scope; the caller
  owns it (`using`).

### `NumpyExtensions` + `ByteContract` (`Pythonic.cs`) — the byte oracle
- On a `PyObject`: `.dtype_str()`, `.shape_dims()`, `.strides_bytes()`, `.writeable()`, `.astype(s)`,
  and **`.bytes_c()`** = `np.ascontiguousarray(a).tobytes('C')` — the canonical C-order bytes.
- `ByteContract.NsBytes(nd)` — a NumSharp array's canonical C-order bytes, read **independently** of
  the interop's `ToNumpy` (through NumSharp's own `ascontiguousarray` + a raw copy), so a match is a
  genuine cross-check, not a tautology.
- **`ByteContract.AssertSameBytes(NDArray ns, PyObject expected)`** — NumSharp vs numpy, byte-for-byte.
- **`ByteContract.AssertSameBytes(PyObject a, PyObject b)`** — numpy vs numpy (encode round-trips).

Byte equality is the **strongest** equality: it catches dtype width, endianness, layout
linearization and padding that a value compare (`np.array_equal`) silently accepts. Because
`bytes_c()` C-orders both sides first, a **layout-only** difference (e.g. `qr(mode='raw')`'s `h` is
C-contiguous in NumSharp but an F-view in numpy) is normalized away and only the VALUES are asserted.

## 3. What to reach for

| You want to prove… | Use |
|---|---|
| NumSharp op == numpy op, same bytes | build in NumSharp → `a.ToNumpy()` → `Python.np.with("np.OP(a)", ("a", va))` → `ByteContract.AssertSameBytes(ns, np_)` |
| numpy reads a strided/broadcast export correctly | export the VIEW (`nd.T.ToNumpy()`, `broadcast_to(...).ToNumpy()`); numpy computes over it |
| a crossing carries the right bytes | `ByteContract.AssertSameBytes(exported, expected)` (numpy↔numpy) |
| a semantic predicate | `Python.np.truthy("np.isnan(a).all()", ("a", va))` |
| the input is identical on both sides | build ONCE in NumSharp, export; or build in numpy and `ImportOf` — either way the bytes are shared |

## 4. Why it is byte-exact — and the three levers that decide it

Two classes of op:

- **Backend-independent** (integer/bool elementwise, reductions, matmul; float `negative`/`abs` —
  pure sign-bit): associative-exact or bit-defined, so byte-equal on *every* host regardless of which
  BLAS is installed. `NumpyComputeInteropTests` lives here.
- **BLAS/LAPACK-backed** (`dot`, `matmul` float, `linalg.{cholesky,qr,inv,solve,det,slogdet,svd,…}`):
  the bits depend on **three levers** —
  1. **the OpenBLAS build**,
  2. **the worker-thread count**,
  3. **the dispatched DYNAMIC_ARCH micro-kernel** (a property of the running CPU).

  Byte-parity holds only when all three agree between the two stacks. This project makes them agree:
  - NumSharp **bundles the scipy-openblas build NumPy 2.4.2 pins** (verified byte-identical), so on a
    NumPy-2.4.2 host both call the **same binary** (lever 1).
  - `PythonSession` enables the backend at **`threads: 1`** (lever 2), and the test matrices are kept
    **small enough that OpenBLAS stays single-threaded on both sides** regardless — so the answer is
    deterministic.
  - Same process, same CPU ⇒ same micro-kernel (lever 3).

  There is deliberately **no tolerance fallback** for these ops: if a host's NumPy uses a materially
  different BLAS, the byte assertion *should* go red — that is the gate doing its job. Keep matrices
  small (this is a correctness gate, not a benchmark); the offline `matmul_parity` corpus is where
  large host-pinned cases live.

**float32/complex64 note:** NumPy's `linalg` is "lite" — it computes *every* factorisation in
double/cdouble and casts the result back (`_commonType`), so a float32 operand is factorised with the
double routine and rounded once. NumSharp's backend reproduces that exactly, so a float32 result is
byte-identical too. Likewise integer/bool operands widen to float64 on both sides.

**Windows C-long trap:** a reduction's accumulator is the C `long` (32-bit on standard-CPython
Windows, 64-bit on unix), so `numpy.sum(int32)` is int32 on `windows-latest` but int64 elsewhere.
Run integer reductions at **int64** so the byte compare is width-identical on all three CI OSes
(NumSharp is always int64). Products/factorisations don't hit this (they run in float64).

## 5. Error parity

NumPy raises `numpy.linalg.LinAlgError` (a `ValueError` subclass); pythonnet surfaces it as a
`PythonException`. NumSharp raises its typed `LinAlgError`. Assert both, with the same verbatim text:

```csharp
new Action(() => np.linalg.cholesky(bad)).Should().Throw<LinAlgError>()
    .WithMessage("Matrix is not positive definite");
using (Gil())
{
    using PyObject va = bad.ToNumpy();
    new Action(() => { using var _ = Python.np.with("np.linalg.cholesky(a)", ("a", va)); })
        .Should().Throw<PythonException>().WithMessage("*Matrix is not positive definite*");
}
```

NaN/inf: `potrf`/`geqrf` in the shared binary decide `info` identically on both sides, so a NaN
diagonal that returns `info=0` yields the same NaN-propagated factor (no raise) in both — verify it,
don't assume it raises.

## 6. GIL discipline (pitfalls that cost hours)

- **Anything touching a `PyObject` runs under the GIL** — including its `Dispose` (pythonnet 3.0.x's
  final decref runs `PyErr_Fetch`). Create AND dispose each `PyObject` inside one `using (Gil())`.
- Tests hold **NumSharp arrays and plain CLR values** outside the GIL; open `Gil()` only around the
  Python part. Compute the NumSharp side first (no GIL), then open the GIL for the export + numpy call
  + byte compare.
- Don't let a `PyObject` escape its GIL scope into a `using` that disposes later outside it.
- GC-lifecycle tests need `Pump()`/`WaitFor()`/`Settle()` (CLR GC + finalizers + pythonnet
  deferred-decref + a Python `gc.collect()`); the base drives these for the leak gate.

## 7. Adding a live-parity test for a new op

1. Derive from `InteropTestBase`.
2. Guard the backend if the op needs one: `if (!OpenBlasEngine.LapackAvailable) Assert.Inconclusive(...)`
   (BLAS products/`linalg` factorisations). Pure-managed ops need no guard.
3. Build the input in NumSharp across the axes that matter — **dtypes** (all 15; widening + native +
   complex), **layouts** (C/F/transposed/reversed/strided/broadcast — export the VIEW), **shapes**
   (tall/wide/square, batched 3-D/4-D, 1×1, empty/degenerate), **modes/params**.
4. `using (Gil())`: `a.ToNumpy()`, `Python.np.with("np.OP(a[, params])", ("a", va))`,
   `ByteContract.AssertSameBytes(ns, np_, because)`.
5. Cover the **error taxonomy** too (both stacks raise, same message).
6. Keep matrices small (correctness gate). Dispose every `PyObject`.

`CholeskyQrLiveParityTests` (cholesky/qr) and `LapackDifferentialTests` (the LU family —
solve/inv/det/slogdet/matrix_power/tensorinv/tensorsolve, across dtypes/layouts/batch/edge/error) are
the templates. Offline value gates for the same
ops live in `test/NumSharp.Tests/Backends/*FactorisationTests.cs` (they run without Python and
assert to a tolerance for cross-machine robustness); this project is the *byte-exact, live* half.

## 8. Running

```bash
cd test/NumSharp.Tests.Interop

# All interop tests (needs Python+numpy discoverable; embeds CPython — slower than the managed suite)
dotnet test -f net10.0

# Just the cholesky/qr live-parity gate
dotnet test -f net10.0 --filter "ClassName~CholeskyQrLiveParityTests"

# Point at a specific interpreter's shared library
PYTHONNET_PYDLL=/path/to/python312.dll dotnet test -f net10.0

# On a box without Python: skip instead of fail
NUMSHARP_PYTHONNET_REQUIRE_ENGINE=0 dotnet test -f net10.0
```

Backend discovery honours the usual `NUMSHARP_OPENBLAS_*` knobs (`NUMSHARP_OPENBLAS_LIBRARY` binds one
specific CBLAS — point it at the numpy wheel's own `libscipy_openblas*` to *guarantee* lever 1 on a
non-2.4.2 host; `NUMSHARP_OPENBLAS_USE_BUNDLED=0` drops the bundle). CI's interop job installs
Python+numpy and sets `NUMSHARP_PYTHONNET_REQUIRE_ENGINE`, so a discovery break there goes red rather
than green-by-skipping.

## 9. Why this over the offline corpus?

The offline oracle (`test/oracle/`) is the right tool for the bulk NDIter-backed surface: it needs no
Python at test time, so it runs on every CI image and pins a reproducible snapshot. This project
complements it where the extra cost of an embedded engine buys something the snapshot can't:

- **the crossing itself** — numpy computing over NumSharp's *actual exported memory* (proves the
  export's dtype/shape/strides are right, not just that a value matches a recorded byte),
- **the installed NumPy** — parity against whatever numpy is on the machine, live, not a 2.4.2
  snapshot,
- **round-trip fidelity** — export → numpy kernel → import, end to end.

Same philosophy as the rest of the repo — **NumPy is the source of truth** — but here we ask it to
compute the answer live and match it to the last byte.
