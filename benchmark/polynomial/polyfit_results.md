# numpy.polynomial least-squares fits (U6: {p}fit) — NumSharp vs NumPy 2.4.2

Generated by `benchmark/polynomial/polyfit_report.py` from `polyfit_bench.cs` runs. **NPY/NS = NumPy time /
NumSharp time — higher is better, > 1 means NumSharp is faster.** Every cell's result was compared byte for byte
(SHA-256 of dtype, shape and data of every slot, the four `full=True` statistics included) against NumPy's before it
was timed: all 29 cells are bit-exact.

Method: both sides pinned to the same two P-cores (`NS_PROBE_AFFINITY=0x14`), never concurrently, OpenBLAS at ONE
thread on both sides (NumPy under `OPENBLAS_NUM_THREADS=1`, NumSharp through `NumSharp.Interop.OpenBLAS`, the same
scipy-openblas build); C# in Release with `DOTNET_TC_CallCountingDelayMs=0` and a drained tier-1 warm-up;
best-of-rounds per side, and the per-cell best over 3 alternating NumPy / NumSharp run pairs.
Host: Intel64 Family 6 Model 183 Stepping 1, GenuineIntel, Windows 11.

**The lstsq ceiling.** A fit is NumPy's `_fit` statements around ONE `np.linalg.lstsq` call, and both libraries run
that call through the same LAPACK `gelsd`. The `lstsq` columns time that call alone, on the operands `_fit` hands
it; `ceiling` = NumPy's whole call over NumSharp's lstsq alone — the NPY/NS a fit would reach if every statement
NumSharp owns took no time. `lstsq share` is the part of NumSharp's call spent in lstsq. As the degree grows gelsd
takes over both calls (its work grows as n x (deg + 1)^2), so the ratio falls toward the ceiling, and where the
ceiling itself is under 1.5x no composition can reach 1.5x: the remaining gap is NumPy's own statements against
NumSharp's, which run 2-4x faster than NumPy's (the fused norm pass, the one-kernel Vandermonde matrix, the
C-ordered column scaling).
