## Findings

### QA-01 — a slice with step 0 selects nothing instead of raising (S2)

- `a["::0"]`, `a["1:8:0"]`, `a[new Slice(0, 5, 0)]` return an empty view; `a["::0"] = 5` returns normally and writes
  nothing. NumPy: `ValueError: slice step cannot be zero` for every one of them.
- Root cause: `Slice.ToSliceDef` (`src/NumSharp.Core/View/Slice.cs`) answers `Step == 0` with
  `new SliceDef { Count = 0 }`.
- Fix size: small (raise `ValueError("slice step cannot be zero")` there, or when the `Slice` is built; check
  `np.s_` / `np.r_` slices, which reach the same type).
- Pinned: `ParityQa_Slice_ZeroStep_Get_ShouldRaiseValueError`, `ParityQa_Slice_ZeroStep_Set_ShouldRaiseValueError`.

### QA-02 — `np.nonzero` of a 0-d numeric array answers instead of raising (S2, owner's call)

- `np.nonzero(np.array(5))` and `np.array(0.0).nonzero()` return `(array([0]),)` / `(array([], int64),)`. NumPy 2.4.2:
  `ValueError: Calling nonzero on 0d arrays is not allowed. Use np.atleast_1d(scalar).nonzero() instead.`
- Deliberate: `DefaultEngine.NonZero` (`Backends/Default/Indexing/Default.NonZero.cs`) keeps the old answer to avoid a
  breaking change, while the text dtypes, `NDListArray` and numpy.ma already raise NumPy's error. Principle 4 of the
  project instructions accepts breaking changes that align with NumPy 2.x, hence the question in Open questions.
- Fix size: small. Pinned: `ParityQa_Nonzero_ZeroDimNumeric_ShouldRaiseValueError`.

### QA-03 — `np.tril` / `np.triu` of a 0-d array throw `ArgumentException`, NumPy `TypeError` (S4)

- Same text (`tri() missing 1 required positional argument: 'N'`), wrong type: `NDArray.TwoDimBase.cs` line ~388 throws
  `ArgumentException`; `Indexing/np.tri.Test.cs` asserts the current type.
- Fix size: trivial (`throw new TypeError(...)` + the unit test). Pinned: `ParityQa_TrilTriu_ZeroDim_ShouldRaiseTypeError`.

### QA-04 — `np.around(bool, decimals != 0)` throws `NotSupportedException`, NumPy `UFuncTypeError` (S4)

- NumPy's text is reproduced (`Cannot cast ufunc 'multiply' output from dtype('float64') to dtype('bool') with casting
  rule 'same_kind'`; `'divide'` for a negative `decimals`) but the type is `NotSupportedException`, neither NumPy's
  `TypeError` nor the house `ArgumentException` the rules name for ufunc cast refusals.
- Fix size: small. Pinned: `ParityQa_Around_BoolWithDecimals_ShouldRaiseTypeError`.

### QA-05 — computed NumPy scalars (`a[i]`, `a.sum()`, `np.array(x)`) are WEAK operands in the binary ufuncs (S1, known)

- NEP 50: every NumPy scalar and 0-d array is strong. NumSharp reads ANY 0-d operand beside an array as a Python literal.
  Measured (`p04`, 23 of 29 calls differ): `u8 + i64[1]` → uint8 `[201, 202, 194]` (NumPy int64 `[201, 202, 450]`:
  silent wrap); `np.left_shift(i8, np.array(9L))` → int8 zeros (NumPy int64 `[512, -1024, 1536]`); `f16 * f32.mean()`
  → float16 (NumPy float32); `f32 + f64.max()` → float32 (NumPy float64); `np.add(i8, i64.sum())` and
  `i8 * np.array(1000L)` → OverflowError "Python integer 600 out of bounds for int8" (NumPy computes int64);
  `np.clip(i8, i64[0], i64[1])` → int8. `np.result_type`, `np.where`, the comparisons' strong 0-d-vs-0-d case and
  `np.concatenate` are right.
- Known: ufuncs.md / comparison.md document the 0-d rule as a divergence because "a strong 0-d NDArray cannot be told
  from a literal". That stopped being true with `51abf1ad` (plan X27): the implicit conversions mark a C# literal's 0-d
  array `NDArray.WasPythonLiteral` (only the store paths read the mark today). Library code that passes
  `NDArray.Scalar` operands expecting the weak reading would have to move to the mark too.
- Fix size: medium-large (a library-wide promotion rule; every internal `NDArray.Scalar` operand must be audited).
  Pinned: `ParityQa_ComputedScalarOperand_ShouldBeStrong_NoSilentWrap`, `ParityQa_ReductionResultOperand_ShouldBeStrong`.

## Observations (not pinned)

- `np.fft.fftshift` / `ifftshift` of a 0-d array return the value; NumPy raises `ValueError: not enough values to
  unpack (expected 2, got 0)` from its own `np.roll(x, [], ())` (an accident of NumPy's implementation, not a contract).
- `NDLogAddExpMath`'s XML summary says "float32 logaddexp is bit-exact", but `np.logaddexp(float32 -3.0, 0.001)` is
  `0.04953995` (NumPy `0.049539946`, 1 ULP). The oracle excuses logaddexp at ≤ 2 ULP (MisalignedRegistry), so only the
  doc comment is wrong.
- In-place operators: C# `v += x` on a view variable `v` rebinds `v` to a new array (`v = v + x`), so the viewed array
  is unchanged; NumPy's `+=` writes through the view. `a["1:"] += x` works (the indexer setter writes back). C# 14's
  user-defined compound assignment operators could close this.
- Already pinned elsewhere and seen again: median / nanmedian of a lone `-0.0` (`OpenBugs.Reductions.cs`), complex
  transcendental functions within the documented ≤ 3-ULP envelope (`sinc`, `sin`), managed dot / corrcoef summation
  order, `np.partition`'s unordered sides, complex64 results (one complex width).
