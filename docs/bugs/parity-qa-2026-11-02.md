# NumPy parity QA journey — 2026-11-02 / 03

A deep manual QA pass over NumSharp on branch `strings` (base `23ce02ea`), looking for behaviour that differs from
NumPy 2.4.2. Every confirmed divergence gets an id (`QA-NN`), an explanation below and an `[OpenBugs]` reproduction in
[`test/NumSharp.Tests/OpenBugs.ParityQa.cs`](../../test/NumSharp.Tests/OpenBugs.ParityQa.cs). Nothing found here is
fixed in this pass unless it is trivial: the owner decides which ones to fix.

- Window: 2026-11-02 21:51 → 2026-11-03 05:51 (local clock of the session, 8 hours).
- Method: a probe harness (session scratchpad, `probes/`): each direction is a C# probe script run by `dotnet run`
  against `src/NumSharp.Core` and a NumPy twin script printing the same `name|kind|dtype|shape|values` lines; a comparer
  reports dtype, shape, value (exact, NaN-blind unless asked, signed zero kept), error-vs-value and error-type
  differences. Every reported difference is re-checked by hand before it becomes a finding; known, documented
  divergences (`[Misaligned]`, the divergence ledger `test/NumSharp.Tests.Oracle/Fuzz/README.md`, existing
  `[OpenBugs]` pins, a 0-d array where NumPy returns a scalar) are not findings.
- Severity: **S1** silent wrong value / memory unsafety; **S2** crash or refusal where NumPy computes (or computes where
  NumPy refuses); **S3** wrong dtype / shape / layout / flags; **S4** error type or message text.

## Findings

### QA-01 — a slice with step 0 selects nothing instead of raising (S2)

- `a["::0"]`, `a["1:8:0"]`, `a[new Slice(0, 5, 0)]` return an empty view; `a["::0"] = 5` returns normally and writes
  nothing. NumPy: `ValueError: slice step cannot be zero` for every one of them.
- Root cause: `Slice.ToSliceDef` (`src/NumSharp.Core/View/Slice.cs`) answers `Step == 0` with
  `new SliceDef { Count = 0 }`.
- Fix size: small (raise `ValueError("slice step cannot be zero")` there, or when the `Slice` is built; check
  `np.s_` / `np.r_` slices, which reach the same type).
- Pinned: `ParityQa_Slice_ZeroStep_Get_ShouldRaiseValueError`, `ParityQa_Slice_ZeroStep_Set_ShouldRaiseValueError`.

### QA-02 — `np.nonzero` of a 0-d numeric array answers instead of raising (S2, owner's call)

- `np.nonzero(np.array(5))` and `np.array(0.0).nonzero()` return `(array([0]),)` / `(array([], int64),)`. NumPy 2.4.2:
  `ValueError: Calling nonzero on 0d arrays is not allowed. Use np.atleast_1d(scalar).nonzero() instead.`
- Deliberate: `DefaultEngine.NonZero` (`Backends/Default/Indexing/Default.NonZero.cs`) keeps the old answer to avoid a
  breaking change, while the text dtypes, `NDListArray` and numpy.ma already raise NumPy's error. Principle 4 of the
  project instructions accepts breaking changes that align with NumPy 2.x, hence the question in Open questions.
- Fix size: small. Pinned: `ParityQa_Nonzero_ZeroDimNumeric_ShouldRaiseValueError`.

### QA-03 — `np.tril` / `np.triu` of a 0-d array throw `ArgumentException`, NumPy `TypeError` (S4)

- Same text (`tri() missing 1 required positional argument: 'N'`), wrong type: `NDArray.TwoDimBase.cs` line ~388 throws
  `ArgumentException`; `Indexing/np.tri.Test.cs` asserts the current type.
- Fix size: trivial (`throw new TypeError(...)` + the unit test). Pinned: `ParityQa_TrilTriu_ZeroDim_ShouldRaiseTypeError`.

### QA-04 — `np.around(bool, decimals != 0)` throws `NotSupportedException`, NumPy `UFuncTypeError` (S4)

- NumPy's text is reproduced (`Cannot cast ufunc 'multiply' output from dtype('float64') to dtype('bool') with casting
  rule 'same_kind'`; `'divide'` for a negative `decimals`) but the type is `NotSupportedException`, neither NumPy's
  `TypeError` nor the house `ArgumentException` the rules name for ufunc cast refusals.
- Fix size: small. Pinned: `ParityQa_Around_BoolWithDecimals_ShouldRaiseTypeError`.

### QA-05 — computed NumPy scalars (`a[i]`, `a.sum()`, `np.array(x)`) are WEAK operands in the binary ufuncs (S1, known)

- NEP 50: every NumPy scalar and 0-d array is strong. NumSharp reads ANY 0-d operand beside an array as a Python literal.
  Measured (`p04`, 23 of 29 calls differ): `u8 + i64[1]` → uint8 `[201, 202, 194]` (NumPy int64 `[201, 202, 450]`:
  silent wrap); `np.left_shift(i8, np.array(9L))` → int8 zeros (NumPy int64 `[512, -1024, 1536]`); `f16 * f32.mean()`
  → float16 (NumPy float32); `f32 + f64.max()` → float32 (NumPy float64); `np.add(i8, i64.sum())` and
  `i8 * np.array(1000L)` → OverflowError "Python integer 600 out of bounds for int8" (NumPy computes int64);
  `np.clip(i8, i64[0], i64[1])` → int8. `np.result_type`, `np.where`, the comparisons' strong 0-d-vs-0-d case and
  `np.concatenate` are right.
- Known: ufuncs.md / comparison.md document the 0-d rule as a divergence because "a strong 0-d NDArray cannot be told
  from a literal". That stopped being true with `51abf1ad` (plan X27): the implicit conversions mark a C# literal's 0-d
  array `NDArray.WasPythonLiteral` (only the store paths read the mark today). Library code that passes
  `NDArray.Scalar` operands expecting the weak reading would have to move to the mark too.
- Fix size: medium-large (a library-wide promotion rule; every internal `NDArray.Scalar` operand must be audited).
  Pinned: `ParityQa_ComputedScalarOperand_ShouldBeStrong_NoSilentWrap`, `ParityQa_ReductionResultOperand_ShouldBeStrong`.

### QA-06 — `np.cumsum` / `np.nancumsum` along an axis with an integer `dtype=` cast floats by saturation (S1)

- `np.cumsum([-3.0, 1.0], axis=0, dtype=np.uint8)` → `[0, 1]`; NumPy `[253, 254]` (C's float → integer cast, which
  wraps on x86-64). `np.cumsum([[300.0, 1.0]], axis=1, dtype=np.int8)` → `[127, -128]`; NumPy `[44, 45]`. inf / NaN /
  1e10 give MaxValue / 0 where NumPy gives INT_MIN truncated to the width (0 for 8- and 16-bit). Measured (`p09`): 39 of
  64 calls differ, every integer dtype, float64 / float32 / float16 / complex inputs, axis 0 and 1, 1-D with `axis=0`,
  `ndarray.cumsum(axis, dtype)`, `np.nancumsum(axis=...)`. The flat form (no axis), `np.sum` / `np.prod` / `np.mean` /
  `np.cumprod` with `dtype=` on every route (`p10`: axis, None, `where=`, `initial=`), `astype`, setitem, `copyto`,
  `put` / `place` / `putmask`, `full`, `fill` (`p11`) all match NumPy.
- Root cause: the axis scan kernel `ILKernelGenerator.ScanAddWiden` converts each element with `ConvIn` →
  `TAccum.CreateTruncating(TIn)` (`Backends/Kernels/ILKernelGenerator.Reduction.cs`), which saturates a floating-point
  source on net8.0 and net10.0 alike. `TypedSumKernel` / `TypedProdKernel` / `TypedMin/MaxKernel` share `ConvIn` but no
  float → integer route reached them in these probes.
- Fix size: small (convert through the library's NumPy cast for float sources, as the flat route does).
- Pinned: `ParityQa_CumsumAxis_IntegerDtype_ShouldCastLikeNumPy`, `ParityQa_NancumsumAxis_IntegerDtype_ShouldCastLikeNumPy`.

### QA-07 — `np.choose` promotes its choices left to right (S3)

### QA-09 — `np.cumprod` along a length-1 axis keeps a narrow integer dtype (S3)

### QA-10 — complex `np.prod` / `np.cumprod` multiply with the elementwise SIMD form (S1, 1 ULP)

- NumPy's reduce / accumulate run `CDOUBLE_multiply`'s MSVC-contracted `loop_scalar`
  (`im = fma(a.im, b.re, round(a.re*b.im))`); the elementwise `simd_cmul` is `im = fma(a.re, b.im, round(a.im*b.re))`.
  NumSharp's plain `np.prod` and all of `np.cumprod` use the elementwise form (only the `initial=` / `where=` path of
  `np.prod` has the reduce form). `x = -3+1e10j`: `x**4` imaginary part NumPy `1.2e+31`, NumSharp
  `1.2000000000000001e+31` (exact-fraction check: the simd form gives NumSharp's bits, the contracted scalar form
  NumPy's). Random complex inputs (`p12`): imaginary parts differ by one ULP at several of 64 cumprod positions, flat,
  axis 0 and axis 1.
- Fix size: small (the reduce form exists in `Default.Reduction.AddMul.Keywords.cs`).
- Pinned: `ParityQa_ComplexProdAndCumprod_ShouldUseNumPysReduceMultiplyForm`.

### QA-11 — `np.compress` checks a too-long condition even when an earlier axis is empty (S2, low)

- `np.compress([True, False, True], np.zeros((0, 2)), axis=1)` and the same over `(1, 0, 2)` with `axis=-1` throw
  `IndexOutOfRangeException` ("index 2 is out of bounds for axis 1 with size 2"); NumPy returns the empty result.
  NumPy's `PyArray_TakeFrom` validates indices inside the loop over the dimensions before the axis, which runs zero
  times when one of them is 0; NumSharp's `np.take` follows that (`take_empty_oob` matches), compress does not.
- Root cause: the "OOB-True detection" block in `UnmanagedStorage.ItemSelection.cs` (compress) runs before any size
  test. Fix size: trivial (skip it when the leading extent is 0).
- Pinned: `ParityQa_Compress_EmptyLeadingAxis_LongCondition_ShouldReturnEmpty`.

### QA-12 — `NDArray.SetValue<T>` / `itemset<T>` with another element type write raw bytes (S1, memory unsafety, Release)

- `a.SetValue(2.5, 0)` on a float32 array binds `SetValue<double>(T, params long[])` (C# prefers the exact generic match
  over the converting `SetValue(object, ...)`). Its body is `*((T*)Address + _shape.GetOffset(indices)) = value` behind a
  `Debug.Assert` only (`Backends/Unmanaged/UnmanagedStorage.Setters.cs`), while its doc says "value will be converted".
  Release run (`p18`): float32 `[1, 2, 3, 4]` + `SetValue(2.5, 0)` → `[0, 2.0625, 3, 4]`; `SetValue(2.5, 1)` →
  `[1, 2, 0, 2.0625]` (wrong element, two corrupted); `SetValue(7, 2)` → element 2 = `1e-44` (int bits); int64 +
  `SetValue(9, 1)` → element 0 = `38654705665`; uint8 + `SetValue(258, 1)` → elements 4..7 = `[2, 1, 0, 0]`. The last
  element's write runs past the buffer (heap corruption). `itemset<T>(int[], T)` is the same body (its own
  `//TODO! if T != dtype, we need to cast!`).
- The non-generic `SetValue(object, ...)` says "will be converted" too but throws `InvalidCastException` for a boxed
  double into float32 (its `<exception>` tag admits it).
- The getters read the same way (`p19`, Release): `a.GetValue<double>(1)`, `a.GetAtIndex<double>(1)` and
  `a.GetDouble(1)` on float32 `[1, 2, 3, 4]` all return `512.0001225471497` (elements 2 and 3 as one double); `GetDouble`'s
  doc promises a `NullReferenceException` for another dtype. `a.item<double>(1)` converts correctly. Debug.Assert-only
  type checks also guard `AsSpan<T>` / `AsUnmanagedSpan<T>` / `SetAtIndexUnsafe<T>` (`UnmanagedStorage.cs`,
  `UnmanagedStorage.Setters.cs`).
- Known relative: the `SetAtIndex<T>` trap (CLAUDE.md library-wide traps, pinned in `OpenBugs.Surface.cs`); these two
  public members were not listed with it, and `SetValue` is the commonly used one.
- Fix size: small (convert through the storage's NumPy cast when `typeof(T) != dtype`, or refuse).
- Pinned: `ParityQa_SetValueGeneric_OtherElementType_ShouldCastNotWriteRawBytes` (Release-only, Inconclusive in Debug
  like the `SetAtIndex` pin).

### QA-19 — complex `np.clip` propagates a bound's NaN imaginary part and keeps x on an upper-bound tie (S1)

  `"(n)->(),()"`, or more than three core arguments) calls the delegate through `DynamicInvoke`, so the caller gets
  `TargetInvocationException: Exception has been thrown by the target of an invocation.` with the user's exception as
  the inner one; a `catch` for the user's own type misses it.
- Fix size: one line (unwrap with `ExceptionDispatchInfo.Capture(e.InnerException).Throw()`). Pinned:
  `ParityQa_VectorizeSignatureFallback_ShouldPropagateTheCallbacksException`.

### QA-44 — `np.divmod(out=(input, r))` computes the remainder from the overwritten input (S1)

- NumPy's divmod is one two-output loop: each element is read once and both results are written, so an out that is
  also an input is safe: `np.divmod(a, 2.0, out=(a, r))` for `a = [7.5, -7.5, 3.0]` leaves `a = [3, -4, 1]` and
  `r = [1.5, 0.5, 1.0]`.
- NumSharp's `out=` route composes the two ufuncs (ufuncs.md: "Its out=(q, r) / where= / dtype= path composes
  FloorDivide and Mod"), so the floor division overwrites `a` before the remainder reads it: `r = [1, 0, 1]`, the
  remainders of the quotients (`p112`, `rp12`). A quotient out aliasing the divisor (`out=(b, r)`) is the same case.
  A remainder out aliasing an input, partial outs (`(q, None)`, `(None, r)`), `where=`, a float out for an integer
  divmod, and np.modf / np.frexp with any aliased or partial out (single loops) all match NumPy.
- Fix size: small (compute both outputs in one pass on the out= route, as the fused no-out kernel does, or copy an
  input that the quotient out overlaps). Pinned: `ParityQa_DivmodOut_QuotientAliasingAnInput_ShouldReadTheOriginalInput`.

### QA-45 — `np.array` over a ragged jagged array truncates silently; over `NDArray[]` it refuses (S1, S2)

- NumPy refuses a ragged nested sequence (`np.array([[1], [2, 3]])`: `ValueError: setting an array element with a
  sequence. The requested array has an inhomogeneous shape after 1 dimensions. The detected shape was (2,) +
  inhomogeneous part.`) and stacks a list of equal-shape arrays (`np.array([a, b])` is `(2, 3)`; mixed dtypes promote,
  unequal shapes raise the inhomogeneous ValueError).
- NumSharp's typed-array route reads a jagged array with its FIRST row's length (`p114`, `rp13`): a longer later row is
  truncated silently (`np.array(new int[][] { new[] { 1 }, new[] { 2, 3 } })` is `[[1], [2]]`, S1), a shorter one
  throws `IndexOutOfRangeException: Index was outside the bounds of the array.` (a 3-level `double[][][]` too), and
  `np.asarray` of a ragged `long[][]` says `TypeError: buffer is too small for requested array`.
- A typed `NDArray[]` — the C# spelling of a list of arrays — is refused by `np.array` and `np.asarray` with
  `NotSupportedException: Cannot interpret 'NumSharp.NDArray' as a data type: it is not one of NumSharp's element types.`
  (0-d elements too), while `np.asanyarray(NDArray[])` and `np.array(object[])` stack it into NumPy's `(2, 3)` (S2).
- Regular jagged arrays (2- and 3-level, empty rows), `List<double>`, multi-dimensional arrays (a zero extent, 3-D),
  empty containers and bool / string jagged arrays match.
- Fix size: small (validate each row's length while reading a jagged array; route `NDArray[]` to the object-list
  coercion np.asanyarray already uses). Pinned: `ParityQa_ArrayOfRaggedJaggedOrNDArrays_ShouldRefuseOrStackLikeNumPy`.

### QA-46 — `DType == / !=` a string that names no dtype throws instead of answering (S4)

- NumPy's `arraydescr_richcompare` converts the other operand and, when that fails, clears the error and returns
  `NotImplemented`, so Python falls back to identity: `np.dtype('int32') == 'bogus'` is False, `!= 'bogus'` True (also
  `''`, the structured `'i4,i4'`, a number, a list).
- NumSharp's `DType` operators (`DTypes/DType.cs`) take two `DType`s, so a string operand goes through the implicit
  string → DType conversion first, which parses and throws: `NotSupportedException: data type 'bogus' not understood`
  (and the structured-dtype refusal for `'i4,i4'`) from both `==` and `!=` (`rp16`, `rp17`). `DType.Equals("bogus")`
  already answers False, and every parseable spelling (`"int32"`, `"i4"`, `np.int32`, `NPTypeCode.Int32`) compares as
  NumPy's (`typeof(int)` is C#'s int32 by the documented mapping, where Python's `int` is int64).
- Fix size: small (`operator ==` / `!=` overloads for `(DType, string)` that answer False / True when the string does
  not parse). Pinned: `ParityQa_DTypeEqualityWithAnUnparseableString_ShouldAnswerNotThrow`.

## Observations (not pinned)

- `np.fft.fftshift` / `ifftshift` of a 0-d array return the value; NumPy raises `ValueError: not enough values to

  doc comment is wrong.
- In-place operators: C# `v += x` on a view variable `v` rebinds `v` to a new array (`v = v + x`), so the viewed array

- `np.broadcast_to(a, new long[] { 2, 3 })` does not compile: `long[]` converts to both `Shape` and `NDArray`
  (CS0121); callers must write `new Shape(2, 3)`.
- `np.array(a, copy: false)` returns a new view object where NumPy returns `a` itself (`is` identity); the data is
  shared, so only reference identity differs.
- Known and seen again: `NDArray.flat` is a raveled COPY for any non-C-contiguous array, so `a.T.flat[i] = v`,
  `np.asfortranarray(a).flat["0:3"] = v`, stepped and reversed views all drop the write silently (iteration.md documents

  "Actual value was …" decoration after NumPy's text (documented in `AxisArgumentParity.Test.cs`).
- Explicit conversions keep the dtype's cast semantics where NumPy's `int()` raises: `(int)np.array(double.NaN)` is
  `int.MinValue` (NumPy `ValueError: cannot convert float NaN to integer`), `(int)np.array(1e20)` wraps, and
  `(long)np.array(ulong.MaxValue)` is -1 (C# integers cannot hold Python's unbounded int).
- `np.bincount` of a 4e9-range input throws `OutOfMemoryException` ("Insufficient memory to continue the execution of
  the program.") where NumPy raises `MemoryError: Unable to allocate 32.0 GiB for an array with shape (4294967296,) and
  data type int64`; every unallocatable size does the same (`p82`: empty / zeros / ones / arange / full / eye / repeat /
  a broadcast copy). The type is the documented mapping; NumPy's text (size, shape and dtype) is lost.
- `np.putmask` / `np.place` read a 0-d NDArray as a NumPy scalar (selection-indexing.md: "a 0-d array (a NumPy scalar)
  converts without it"); NumPy 2.4.2 tells the two apart: `np.putmask(int8, m, np.array(5))` raises `TypeError: Cannot
  cast scalar from dtype('int64') to dtype('int8') according to the rule 'safe'`, while `np.int64(5)` is stored (`p83`).
  The same scalar-versus-0-d ambiguity as QA-05.
- 353 `throw new ArgumentException(` sites in Core: where NumPy raises `ValueError` (np.diag "Input must be 1- or 2-d.",
  np.power "Integers to negative integer powers are not allowed.", np.fill_diagonal, np.dot's "shapes … not aligned",
  np.repeat's broadcast text) the C# type is plain `ArgumentException`, so `catch (ValueError)` misses them (NumSharp's
  `ValueError` derives from `ArgumentException`, not the reverse).
- Decimal has no NaN / inf: np.std / np.var / np.nanstd / np.nanvar with `ddof >= n` throw `DivideByZeroException`
  ("Attempted to divide by zero.") and np.corrcoef of an empty Decimal array throws `OverflowException` ("Value was
  either too large or too small for a Decimal.") where the float dtypes return NaN.
- `NDArray.transpose(int[] premute = null)`: the parameter is misspelled ("premute"; NumPy's is `axes`), so
  `a.transpose(axes: ...)` does not compile.
- NumPy 2.4.2 bugs NumSharp does not copy: `np.unpackbits(np.array([], np.uint8), count=9)` and
  `np.fft.irfft(np.array([], complex), n=7)` return uninitialized memory in NumPy (different garbage per run);
  NumSharp returns zeros, the documented padding.
- Conventions, not bugs: a C# `int` literal becomes an int32 array where NumPy's Python int becomes int64
  (`np.diff(int16, prepend: 0)` is int32, NumPy int64; `np.full(shape, 7)` int32); a typed C# array is an ndarray, so
  `np.array(double[], int8)` casts like `astype` where NumPy's Python float list raises `OverflowError`.
- Real float NaN SIGNS differ in four places (`p41`), all inside the oracle's stated policy that float16 / float32 /
  float64 NaN signs are non-contractual (only complex unary NaN signs are): `np.hypot(x, +nan)` and `np.hypot(+nan, x)`
  return `-nan` (NumPy propagates the input `+nan`; NumSharp's result is a fresh default NaN at every dtype),
  `np.log1p(x < -1)` returns `-nan` (NumPy `+nan`, every dtype), `np.spacing(-inf)` returns `-nan` (NumPy `+nan`), and
  float32 `np.exp2(-nan)` returns `+nan` (NumPy keeps `-nan`).
- `S.astype(StringDType())` of bytes that are not UTF-8 (`b'a\xff'`): NumPy 2.4.2 copies the raw bytes without checking
  and raises `UnicodeDecodeError` only when an element is read (`np.strings.str_len` of it even answers 1); NumSharp
  raises the same `UnicodeDecodeError` text at the cast (`p78`). NumPy's lazy acceptance stores invalid UTF-8 in a
  StringDType array, which NumSharp's storage could not represent; the owner's call.
- `np.sort` of an array with more than 32 dimensions: NumPy raises `RuntimeError: this function only supports up to 32
  dimensions but the array has 64.` (a legacy iterator limit inside its sort); NumSharp sorts it (`p68`). NumPy's own
  limitation; matching it is the owner's call.
- `np.argsort` with ties: NumPy's default kind (x86-simd-sort's AVX2 networks) is unstable from 4 elements on for the
  32- / 64-bit dtypes and from 17 for the 8- / 16-bit ones (`np.argsort(int32 [2,0,1,1,0,…])` of 15 elements returns
  `[2, 10, 3, 0, 6, …]` where the stable order is `[2, 10, 0, 3, 4, …]`); NumSharp returns the stable order for every
  kind (`p55`). sorting.md states it ("The kind is ignored: every kind gets NumPy's stable (mergesort) order"); the tie
  order of NumPy's unstable kinds is CPU-dependent, so this stays an observation.
- The dense complex128 sample (`p54`, 1M values) against the complex-unary family's documented ≤ 3-ULP envelope: outside
  QA-25 and the documented regimes (arccos / arccosh's sub-DBL_MIN real flush: 6,014 components; subnormal outputs; huge
  arguments), a few interior components exceed it by 1–2 ULP (log10 4 ULP once, tan / arccos / arccosh 5, tanh / sign

  `np.cosh(complex(-709.9726587989646, 1.49e-132))` is `inf - infj` in NumPy (UCRT `ccosh`) and the finite
  `1.0868710547728622e+308 - 1.62e+176j` in NumSharp. NaN signs: no flip anywhere in the sample.
- float-math.md says float32 `np.exp2` is "within 1 ULP of NumPy on every input; the differing inputs all give
  subnormal outputs". Over a dense 4.2M-value sample (`p52`) 215 inputs differ, all by 1 ULP, but 160 of them give
  NORMAL outputs (`exp2(1.3156612e-05)`: NumSharp `1.0000092`, NumPy `1.0000091`; `exp2(0.0051241415)`: `1.003558` vs

  of the sample (exp / log / sin / cos / tanh / the other libm forms / casts / rounding / frexp / modf / hypot / arctan2
  / power / sums) is bit-exact on all 4.2M inputs.
- `np.linalg.solve` of `[[-5e-324, 2.2e-16, -0], [1, 8.99e307, 1.8e308], [-1.8e308, 2.2e-308, -5e-324]]` returns
  `[inf, inf, -1.1e15]` where NumPy raises `LinAlgError: Singular matrix` (`fz12`): LAPACK's second multiplier
  `2^-52 × (1 / 2^1023)` lands exactly on half the smallest subnormal and rounds to 0, so its last pivot is an exact
  zero; the managed LU's elimination order does not reach that zero. Pathological (overflowing operands); ordinary
  singular matrices raise in both (`p17`).
- Already pinned elsewhere and seen again: median / nanmedian of a lone `-0.0` (`OpenBugs.Reductions.cs`), complex
  transcendental functions within the documented ≤ 3-ULP envelope (`sinc`, `sin`), managed dot / corrcoef summation
  order, `np.partition`'s unordered sides, complex64 results (one complex width).
- Read-only refusal wording (`p88`): `np.argmax` / `np.argmin` with a read-only `out=` raise `assignment destination is

  CARRAY | WRITEBACKIFCOPY)` says `WRITEBACKIFCOPY base is read-only` (np.take / np.quantile already use that text). The
  type (ValueError) and the order (shape, cast, then writeability) match. `a.flat[0] = v` on a read-only array says
  `assignment destination is read-only` where NumPy's flatiter says `underlying array is read-only`: `NDArray.flat` is
  documented as a raveled array, not NumPy's flatiter (`a.flatiter` / `np.flat(a)` has NumPy's text).
- `np.squeeze` of a 0-d array returns a new view (`owndata` False); NumPy's `PyArray_Squeeze` returns the array itself
  when there is no unit axis (`owndata` True). An array with axes but no unit axis matches (`p89`, `p90`).
- A `.npy` FILE whose data block is truncated (`p104`): NumSharp says `EOF: reading array data, expected 64 bytes got
  52` (NumPy's text for a non-file stream); NumPy's `read_array` reads a real file with `fromfile` and says `Failed to
  read all data for array. Expected (8,) = 8 elements, could only read 6 elements. (file seems not fully written?)`.

  nothing), trailing bytes after the data (ignored), a truncated header, an empty file, npz key order / `.npy`-suffixed
  keys / missing keys and the `arr_0` name conflict all match.
- `np.ptp(a, axis=0, out=a[0])` (`p113`): NumPy's `_ptp` is `subtract(maximum.reduce(a, axis, out=out),
  minimum.reduce(a, axis), out)`, so the maxima land in the row before the minima are taken from the modified array —
  NumPy returns `[5, 3, 6]` for `[[1, 4, 9], [2, 8, 3], [7, 5, 6]]`; NumSharp returns the true peak-to-peak `[6, 4, 6]`.

  function with an out aliasing its input matches (var / std (ddof) / mean / median / percentile / quantile /
  nanmedian / sum / max along either axis into a row or column, in-place cumsum, dot / matmul / einsum into an
  operand, take / choose into an operand, clip / around / negative into a shifted view, add with a reversed alias).
- `==` / `!=` with a masked array (`p115`, `rp14`, `rp15`): NumPy returns the element-wise masked comparison
  (`a == ma` is `[True -- True]`); NumSharp's `NDMaskedArray` deliberately does not overload them (a code comment in
  `Ma/NDMaskedArray.cs`: they would shadow reference equality; use `np.ma.equal` / `np.ma.not_equal`, which match), so

  NDArray's `==(NDArray, object)` and throws `NotSupportedException: Unable to resolve asanyarray for type
  NDMaskedArray`. Every other operator mix (`+ - * / % < > <= >= & | ^`, NDArray on either side) returns NumPy's masked
  result, and the matrix mixes (`a * m`, `m * a`, np.add / np.dot / np.concatenate of matrix and ndarray) return
  NumPy's classes. A design decision, recorded here, not pinned (np.add / np.where / np.concatenate taking an
  NDMaskedArray do not compile: the class is not an NDArray, numpy.ma's functions are the masked surface).
