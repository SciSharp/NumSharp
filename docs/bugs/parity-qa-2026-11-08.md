### QB-01 — complex `np.sign` divides by np.absolute's magnitude instead of `npy_hypot` (S1, ULP-level)

- Symptom: `np.sign(np.array([-2+7j]))` is `-0.274721127897378+0.961523947640823j`; NumPy 2.4.2 gives
  `-0.27472112789737807+0.9615239476408232j`. Over 20,000 complex values with log-uniform magnitudes (1e-13 … 1e13
  per part), 4,552 (22.8 %) differ by 1–2 ULP in a part; `np.sign(1e-300+1e-300j)` too.
- NumPy: `CDOUBLE_sign` (`_core/src/umath/loops.c.src`) is `in1abs = npy_hypot(in1r, in1i)`, then the zero / NaN /
  infinity branches, then `(in1r / in1abs, in1i / in1abs)`. On win-amd64 `npy_hypot` is the UCRT `hypot`, which
  NumSharp already reproduces exactly (`NDHypotMath`, parity QA-25: `np.hypot` matched all 20,000 pairs here too).
- NumSharp: the complex branch of `DirectILKernelGenerator.EmitSignCall` (`DirectILKernelGenerator.Unary.Math.cs`)
  computes `NDComplexMath.Abs(z)` — np.absolute's SIMD formula `larger * sqrt(fma(ratio, ratio, 1))` — and divides by
  it (`Complex / double`, the same per-part division as NumPy). The zero / NaN / infinity branches are right.
  Computing `np.real(z) / np.hypot(re, im)` and `np.imag(z) / np.hypot(re, im)` with NumSharp's own kernels matches
  NumPy on all 20,000 values, so the fix is one helper call (`NDHypotMath`'s UCRT model in place of
  `NDComplexMath.Abs`).
- Why no gate caught it: `MisalignedRegistry`'s branch (6b) "complex unary within 3 ULP (full NumPy-algorithm port)"
  excuses every one-operand complex op not in `ByteExactArithmeticUnaryOps`; it was written for the transcendental
  `npy_c*` ports, and `sign` has no transcendental step. Adding `sign` to the byte-exact set would gate the fix.
- Pin: `ParityQb_QB01_ComplexSign_DividesByNpyHypot`. Fix size: one line (plus the registry entry).

### QB-02 — `np.arange`'s C# `float` overloads return float32 computed in float32 (S3 dtype, S1 values)

- Symptom: `np.arange(0f, 1f, 0.1f)` is a float32 array `[0, 0.1f, 0.2f, 0.30000001192092896f, …]`;
  `np.arange(3.5f)` is float32 `[0, 1, 2, 3]`.

- Symptom: float32 / float16 `np.median` / `np.percentile` / `np.quantile` (every method, the selecting `lower` /
  `nearest` included, flat and per axis) return a slice's signalling NaN quieted (`0xff800789` → `0xffc00789`); NumPy
  returns it untouched. `np.prod` of one element (flat or along a length-1 axis) returns a signalling NaN still
  signalling (NumPy quiets it). `np.cumsum` / `np.cumprod` quiet a signalling NaN in the first position (NumPy copies
  it). float64 quantiles already keep it.
- NumPy: `_median_nancheck`'s `data.take(-1)` and `_quantile`'s `arr[-1]` hand the element back as it is; the product
  reduction starts from the identity (`1 * x` quiets); the accumulate copies its first element.
- NumSharp: the float32 / float16 quantile kernels pass the NaN through a conversion; the size-1 product copies (the
  real-dtype face of `Prod_OneComplexElement_IsTheIdentityTimesTheElement`); the scans seed with the identity (the root
  cause of `CumSum_Flat_KeepsFirstNegativeZero_LikeNumPysAccumulate` / `CumProd_Complex_CopiesTheFirstElement`).
- Pin: `ParityQb_QB18_SignallingNaN_ThroughQuantilesProductsAndScans`. Fix size: small each; the last two fall out of
  the existing pins' fixes.

### QB-19 — a fancy assignment whose VALUE shares memory with the destination reads it while writing (S1)

- Symptom: `a = np.arange(10); a[[1, 2, 3, 4]] = a[:4]` gives `[0, 0, 0, 0, 0, 5, …]` (NumPy `[0, 0, 1, 2, 3, 5, …]`):
  each store feeds the next. Every dtype; 1-D index arrays of any integer type and a raw `long[]`; permutations
  (`a[[2, 0, 1]] = a[:3]`), duplicates, negative indices, `a[np.arange(1, 10)] = a[:9]` (all zeros), rows of a 2-D
  array (`M[[1, 2]] = M[:2]`), coordinate pairs (`M[[0, 1, 2], [1, 2, 0]] = M[0]`).
- NumPy: `array_assign_subscript` (`_core/src/multiarray/mapping.c`) copies a value that may share memory with the
  array (`solve_may_share_memory(self, tmp_arr, 1) != 0` → `PyArray_NewCopy`) before any fancy store.
- NumSharp: the fancy setter (`Selection/NDArray.Indexing.Selection.Setter.cs`) has no overlap check; a forward view of
  the destination is read in place. A reversed or strided value is materialized on the way and comes out right, which
  is why the obvious reversal test passes.
- Why no gate caught it: the oracle builds every operand fresh; no corpus case assigns a view of the destination.
- Pin: `ParityQb_QB19_FancyAssignment_CopiesAnOverlappingValue`. Fix size: small (`np.shares_memory`-style test, then
  copy — NumPy's own statement).

### QB-20 — a fancy assignment whose INDEX array is a view of the destination reads the index while writing (S2 / S1)

- Symptom: `a = np.array([2, 0, 1, 3]); a[a[:3]] = 7` raises `IndexError: index 7 is out of bounds for axis 0 with size 4`
  (NumPy `[7, 7, 7, 3]`); `a[a[:3]] = [10, 11, 12]` raises the same (NumPy `[11, 12, 10, 3]`); over `[1, 2, 3, 0]`,
  `a[a] = [5, 6, 7, 8]` raises (NumPy `[8, 5, 6, 7]`) and `a[a] = a` gives `[1, 1, 3, 3]` (NumPy `[0, 1, 2, 3]`);
  `np.put_along_axis(a, a, a * 10, 0)` gives `[1, 10, 3, 30]` (NumPy `[0, 10, 20, 30]`) and
  `np.put_along_axis(a, a, a, 0)` `[1, 2, 3, 0]` (NumPy `[0, 1, 2, 3]`).
- NumPy: the same `array_assign_subscript` copies every index array that may share memory with the destination
  (`solve_may_share_memory(self, indices[i].object, 1)` → `PyArray_Copy`); `put_along_axis` is
  `arr[_make_along_axis_idx(...)] = values`, so it inherits that.
- NumSharp: the index array is read lazily during the stores, so an index already overwritten points elsewhere — an
  error where NumPy computes, or a silent wrong answer. `np.put` and `np.take(out=)` with aliasing indices already
  match.
- Pin: `ParityQb_QB20_FancyAssignment_CopiesAnIndexThatAliasesTheDestination`. Fix size: small (copy aliasing indices up
  front, beside QB-19's value copy).

### QB-21 — a boolean-mask assignment copies a reversed overlapping value where NumPy reads through it (S1)

- Symptom: `a = np.arange(6); a[a >= 0] = a[::-1]` gives `[5, 4, 3, 2, 1, 0]`; NumPy gives `[5, 4, 3, 3, 4, 5]`. A
  forward overlapping view (`a[m] = a[:4]`) is read in place on both sides and matches.
- NumPy: the single-boolean-index branch of `array_assign_subscript` (`HAS_BOOL` → `array_assign_boolean_subscript`) has
  no overlap copy: it streams the value in C order while storing, so a reversed alias re-reads stored elements.
- NumSharp: decides copy-or-alias by the VALUE's layout (non-contiguous → materialized), where NumPy decides by the INDEX
  kind (fancy: copy, QB-19 / QB-20; a single boolean array: read through). NumPy's answer here is an artefact, but it is
  NumPy's answer.
- Pin: `ParityQb_QB21_MaskAssignment_ReadsAReversedOverlappingValueThrough`. Fix size: small, but the owner may prefer to
  document it as a divergence (NumPy's result is order-dependent aliasing).

### QB-22 — `flatiter` assignment does not cycle, cut or flatten its value (S2)

- Symptom: through `a.flatiter` (NumSharp's NumPy-faithful `np.FlatIterator`), `a = np.zeros(6); a.flat[::2] = [1, 2]`
  raises `ValueError: cannot assign 2 input values to the 3 output values where the mask is true` (NumPy
  `[1, 0, 2, 0, 1, 0]`); the same for an index array (`a.flat[[0, 2, 4]] = [7, 8]`), a boolean mask, a longer value
  (`a.flat[1:3] = [1, 2, 3]`: NumPy stores 1, 2), a 2-D target and an empty value (NumPy: a no-op).
- NumPy: `iter_ass_subscript` (`_core/src/multiarray/iterators.c`) walks the value flat and restarts it when it runs out
  (np.put's rule).
- NumSharp: `np.FlatIterator`'s setters demand the exact count (and word the refusal as a boolean-mask assignment).
  (`NDArray.flat`, the raveled-array property, is documented as not NumPy's flatiter and is not part of this finding.)
- Pin: `ParityQb_QB22_FlatiterAssignment_CyclesTheValue`. Fix size: small (one cycling copy loop).

### QB-23 — `flatiter` reads a boolean index array as the integers 0 / 1 (S1)

- Symptom: `np.arange(6).reshape(2, 3).flat[[True, False, True, False, True, False]]` gives `[1, 0, 1, 0, 1, 0]` (NumPy
  `[0, 2, 4]`); a mask of the wrong length is accepted (NumPy: `IndexError: boolean index did not match indexed flat
  iterator along axis 0; size of axis is 6 but size of corresponding boolean axis is 2`); the setter writes every value
  into positions 0 and 1 (`a.flat[a >= 0] = a[::-1]` leaves `[0, 0, 2, 3, 4, 5]`).
- NumPy: a boolean index is `iter_subscript_Bool` / `iter_ass_sub_Bool`, a mask over the flat positions.
- NumSharp: the bool array goes down the integer fancy route after a numeric conversion.
- Pin: `ParityQb_QB23_FlatiterBooleanIndex_IsAMask`. Fix size: small (a mask branch in front of the fancy one).

### QB-24 — `flatiter` indexing with an N-D index array returns a 1-D result (S3)

- Symptom: `np.arange(6).reshape(2, 3).flat[[[0, 5], [1, 2]]]` has shape (4,) (NumPy (2, 2)).
- NumPy: `iter_subscript_int` allocates the result with the index array's dimensions.
- Pin: `ParityQb_QB24_FlatiterIndexArray_KeepsTheIndexShape`. Fix size: a reshape.

### QB-25 — `flatiter` assignment copies an overlapping value / index where NumPy reads through them (S1, aliasing)

- Symptom: `a = np.arange(10); a.flat[1:] = a[:-1]` gives `[0, 0, 1, 2, …]` (NumPy: all zeros); `a.flat[::-1] = a` the
  reversal (NumPy `[0, 1, 2, 3, 4, 4, 3, 2, 1, 0]`); `a.flat[[1, 2, 3, 4]] = a[:4]` `[0, 0, 1, 2, 3, …]` (NumPy
  `[0, 0, 0, 0, 0, …]` — the opposite of ndarray fancy assignment, QB-19); 2-D `m.flat[:] = m.T` and `m.T.flat[:] = m`
  likewise; `a.flat[a[:3]] = 7` over `[2, 0, 1, 3]` gives `[7, 7, 7, 3]` where NumPy raises `IndexError: index 7 is out
  of bounds for size 4`.
- NumPy: `iter_ass_subscript` never copies the value or the index (each element is read when it is stored).
- NumSharp: `np.FlatIterator` materializes both first.
- Pin: `ParityQb_QB25_FlatiterAssignment_ReadsAnOverlappingValueThrough`. Fix size: small; like QB-21, the owner may
  prefer documenting it (NumPy's answer is order-dependent aliasing).

Differences seen and judged not to be findings, with the reason.

- numpy.matrix operands (`d02`): `np.vdot(m, m)` is NumPy's `matrix([[1.]])` (array_vdot's `PyArray_Newshape(-1)`

  plain call. `np.any(m, 0)` binds the typed `NDArray<bool> any(NDArray, int, bool)` overload and returns a plain `(3,)`

  fix).

  (reductions.md "cov is GEMM-bound").
- complex `np.sin` / `np.tanh` differ by 1 ULP on some inputs (`d05`): inside the documented 3-ULP envelope of the
  complex unary ports (registry branch 6b). Measured at scale (`d09`, [-3, 3]²): sin / cos / sinh / cosh differ on ~46 %
  of inputs, tan / tanh on ~30 %, all ≤ 3 ULP. These are NOT blocklisted on MSVC, so NumPy calls the UCRT's `csin` /
  `ccos` / `csinh` / `ccosh` / `ctan` / `ctanh`; the textbook formulas over the UCRT reals (and five variants) do not
  reproduce them (only `cexp` is the textbook `exp(x)·cos(y)`, which NumSharp matches exactly). Not a finding (documented
  envelope), but the root CLAUDE.md sentence "complex128 … its unary ufuncs match NumPy bit for bit" overstates: the
  NaN-sign contract is exact, the finite values are not.
- `np.concatenate(..., dtype=np.int32)` of float64 with `same_kind` raises `InvalidCastException` with NumPy's text

- `np.arange(10, dtype='>f8')` returns native float64: the documented "no non-native storage" divergence.

- `np.sum(a, axis=(0, 2))`: NumSharp reductions take one axis (documented "no tuple axes").
- Stale oracle excuses (a gate hazard, not a parity bug): `MisalignedRegistry` still carries "[known bug]" branches

  inverse-trig / angle refusal, repeat of offset / 0-d views, power uint64 × int64 and float16 widening, empty

  int8 dot, bool min / max along an axis, axis max / min skipping NaN, mixed signed / unsigned result_type with a 0-d
  operand. Each still excuses any case it matches, so a regression of those paths would pass the gate silently;
  removing the branches (after an unfiltered oracle run confirms none fires) would close that. The isscalar(0-d)
  branch is labelled "[known bug]" although `np.isscalar`'s docs make a 0-d NDArray a scalar on purpose.
- Latent, not reachable from the public API (`q08`): the element-reduction ArgMax / ArgMin kernel for complex128
  (`DirectILKernelGenerator.Reduction.Arg.cs`, `ArgMaxComplexHelper` / `ArgMinComplexHelper`) compares MAGNITUDES and its

- `NDPolyBase.Algebra`'s CPython `complex ** int` emulation (n > 100, polar form) uses .NET's `double.Hypot` where CPython
  calls the UCRT hypot (which NumSharp models exactly in `NDHypotMath`); geomspace's complex `out_sign` divides by

- `np.round` does not exist (only `np.round_` / `np.around`): documented in `coverage/overrides.json` (NumPy 2.0
  removed `np.round_`; `np.round` is its 2.x name).
- `ndarray.item()` returns the element's CLR type (`Half`, `float`, `byte`, …) where NumPy returns a Python int / float /
  complex / bool (`q39`), so `(double)np.array(new float[] { 1f }).item()` throws `InvalidCastException` (unboxing a
  float as a double) where `float(a.item())` works in Python. The doc comment promises "a suitable Python scalar"; the
  scalar API is the port map's work package A3, so it is noted, not pinned.
- `np.stack` / `np.vstack` / … have no `out=` / `dtype=` / `casting=` (`q36`): a signature gap the port map lists.
- `np.argpartition`'s INDEX at the kth slot when the kth value is tied (`q41`): 300 of 1,296 probes (every dtype, lines of

- ndarray method forms (`q40`, 55 methods × 8 inputs: NaN, -0.0, int8 wrap, float16 overflow, reversed views, bool,
