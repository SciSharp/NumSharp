# NumPy parity QA journey — 2026-11-08 / 09

A second deep manual QA pass over NumSharp, on branch `journey5` (base `e25b7522`), looking for behaviour that differs
from NumPy 2.4.2. It follows the first journey ([`parity-qa-2026-11-02.md`](parity-qa-2026-11-02.md), QA-01 … QA-55,
all decided) and aims at what that pass could not see: the code that landed after it (the parity batches 1–14
themselves, the subclass redesign, the np.dot / np.vecdot / np.vdot rewrites, the reduction and reversed-operand
kernels, the ufunc result-layout re-port, the Shape copy-keyword refactor, np.evaluate over text), and new techniques
(concurrency, guard pages, size thresholds, layout-invariance metamorphic checks, NumPy's own regression tests).

Every confirmed divergence gets an id (`QB-NN`), an entry below and an `[OpenBugs]` reproduction in
[`test/NumSharp.Tests/OpenBugs.ParityQb.cs`](../../test/NumSharp.Tests/OpenBugs.ParityQb.cs)
(`IssueUrl = "parity-qa-QBNN"`). Nothing found here is fixed in this pass: the owner decides which ones to fix.

- Window: 2026-11-08 22:58 → 2026-11-09 06:58 (local clock of the session, 8 hours).
- Method: a probe harness in the session scratchpad (`h/pq.py`): one probe file per direction, each line
  `name :: <C# expression> :: <NumPy expression>`; the runner generates and builds the C# side against an isolated
  journey5 worktree (Release), runs the NumPy side in process, and compares canonical results — dtype, shape, every
  element bit for bit (NaN-blind unless asked, signed zero kept), the C / F / writeable flags and the array class on
  request, error-versus-value, and the error type and text. Every reported difference is re-checked by hand before it
  becomes a finding. Known, documented divergences (`[Misaligned]`, the divergence ledger
  `test/NumSharp.Tests.Oracle/Fuzz/README.md`, existing `[OpenBugs]` pins, a 0-d array where NumPy returns a scalar,
  the first journey's Observations) are not findings.
- Severity: **S1** silent wrong value / memory unsafety; **S2** crash or refusal where NumPy computes (or computes where
  NumPy refuses); **S3** wrong dtype / shape / layout / flags / class; **S4** error type or message text.

What a user would hit first (the owner's likely fix order):
1. **QB-53** — `np.matmul` / 2-D `np.dot` / `np.tensordot` / `matvec` / `vecmat` / `multi_dot` of two DIFFERENT
   integer dtypes accumulate in double: every element past 2**53 loses bits and an overflow saturates at the dtype's
   minimum instead of wrapping (`int16 @ int32` of 6e9 gives -2147483648, NumPy 1705032704).
2. **QB-61** — `np.hstack(M)` / `np.column_stack(M)` / `np.dstack(M)` / `np.vstack(v)` (and numpy.ma's) read a single
   array as a one-element sequence: silently another shape, where NumPy iterates the array's rows; and
   `np.linalg.multi_dot(stack_of_matrices)` raises where NumPy chains them.
3. **QB-48** — `np.empty_like(a, dtype, 'F')` binds the order char to `Shape` and returns a `(70,)` array.
4. **QB-19 … QB-21, QB-25** — fancy, mask and flatiter assignments whose value or index aliases the destination
   read it while writing (NumPy: as if from a copy, or reads through, per route).
5. **QB-44**, **QB-29** — a C# `long` needle binds searchsorted's `double` overload; C# integer literals bind the FLOAT
   overloads of np.mod / np.remainder / np.linspace.
6. **QB-57 / QB-58** — NEP 50 inside compositions: `np.kron(int8, 2)` wraps 200 to -56 (NumPy promotes to int64);
   `np.concatenate((int8, 300), axis=None)` / `np.union1d(int8, 300)` keep 300 in int32 where NumPy's weak scalar
   wraps to 44 in int8.
7. **QB-55 / QB-56 / QB-59** — NumPy's idioms that do not compile in C#: `np.broadcast_to(x, a.shape)` and
   `np.broadcast_to(5, (2, 3))` (and an NDArray shape is broadcast AGAINST), `np.unravel_index(i, a.shape)`,
   `np.put(a, 0, v)`.
8. **QB-15 … QB-17** — the median family's one-element and short-axis means overflow or round differently.

Techniques, and what each paid:
- Directed probes per direction (rows 22:58 … 02:32): QB-01 … QB-37.

  sort / search, K-order producers, masked printing, programs, interp, exact products, spacing, tuple axes, cross,
  histogramdd): QB-38 … QB-47, QB-52, QB-53.
- Slot capture (every positional slot mismatch of numpy-signature-diff.md called the NumPy way): QB-48, QB-49.
- The NumPy call-form models (simd vs loop_scalar, one-element iterations): QB-50, QB-51.
- C# binding of NumPy's idioms and the ambiguity fuzzer (compile every overloaded group against NumPy-typical
  spellings, harvest CS0121): QB-55, QB-56, QB-59, QB-60 (AD9b), QB-61.
- NEP 50 inside compositions: QB-57, QB-58.
- Clean, and worth keeping as regression ideas: gated fast paths at size boundaries, the buffered cast loop, the
  reduction dtype matrix (2,124 cells), the astype casting matrix (845 cells), int64 / uint64 promotion, Python-int
  bounds through writers, in-place methods, the indexer's spellings, `out=` wider than the loop.

Not findings (see Observations): documented classes (the no-backend product ULP class, argsort's own tie order,
complex64 width, the house exception classes of Open question 1, the C# int = int32 house map), NumPy artifacts not
followed (np.histogram of int64 past 2**53 raising IndexError; OpenBLAS's NaN-pivot answer for det / slogdet / inv),
and spelling differences with a working C# form (tuple arguments).

## Findings

### QB-01 — complex `np.sign` divides by np.absolute's magnitude instead of `npy_hypot` (S1, ULP-level)

- Symptom: `np.sign(np.array([-2+7j]))` is `-0.274721127897378+0.961523947640823j`; NumPy 2.4.2 gives
  `-0.27472112789737807+0.9615239476408232j`. Over 20,000 complex values with log-uniform magnitudes (1e-13 … 1e13
  per part), 4,552 (22.8 %) differ by 1–2 ULP in a part; `np.sign(1e-300+1e-300j)` too.
- NumPy: `CDOUBLE_sign` (`_core/src/umath/loops.c.src`) is `in1abs = npy_hypot(in1r, in1i)`, then the zero / NaN /
  infinity branches, then `(in1r / in1abs, in1i / in1abs)`. On win-amd64 `npy_hypot` is the UCRT `hypot`, which
  NumSharp already reproduces exactly (`NDHypotMath`, parity QA-25: `np.hypot` matched all 20,000 pairs here too).
- NumSharp: the complex branch of `DirectILKernelGenerator.EmitSignCall` (`DirectILKernelGenerator.Unary.Math.cs`)
  computes `NDComplexMath.Abs(z)` — np.absolute's SIMD formula `larger * sqrt(fma(ratio, ratio, 1))` — and divides by
  it (`Complex / double`, the same per-part division as NumPy). The zero / NaN / infinity branches are right.
  Computing `np.real(z) / np.hypot(re, im)` and `np.imag(z) / np.hypot(re, im)` with NumSharp's own kernels matches
  NumPy on all 20,000 values, so the fix is one helper call (`NDHypotMath`'s UCRT model in place of
  `NDComplexMath.Abs`).
- Why no gate caught it: `MisalignedRegistry`'s branch (6b) "complex unary within 3 ULP (full NumPy-algorithm port)"
  excuses every one-operand complex op not in `ByteExactArithmeticUnaryOps`; it was written for the transcendental
  `npy_c*` ports, and `sign` has no transcendental step. Adding `sign` to the byte-exact set would gate the fix.
- Pin: `ParityQb_QB01_ComplexSign_DividesByNpyHypot`. Fix size: one line (plus the registry entry).

### QB-02 — `np.arange`'s C# `float` overloads return float32 computed in float32 (S3 dtype, S1 values)

- Symptom: `np.arange(0f, 1f, 0.1f)` is a float32 array `[0, 0.1f, 0.2f, 0.30000001192092896f, …]`;
  `np.arange(3.5f)` is float32 `[0, 1, 2, 3]`.
- NumPy: arange never returns float32 without `dtype=`. `np.arange(np.float32(0), np.float32(1), np.float32(0.1))`
  and `np.arange(np.float32(3.5))` are float64, filled as `start + i*delta` in double (`[3]` is
  `0.30000000447034836`); a C# `float` read as the house map's Python float gives the same (the float32 value widened
  is the same double).
- NumSharp: `np.arange(float start, float stop, float step = 1)` (region "Original overloads (type inferred from C#
  parameter types)", `Creation/np.arange.cs`) calls `arange(start, stop, step, NPTypeCode.Single)`, and
  `arange(float stop)` forwards to it. The same region's int overloads already return NumPy's int64, and
  `np.linspace(0f, 1f, 5)` (the float overload of linspace) is float64, so the float arange is the one place where a C#
  `float` argument still decides the result dtype.
- Pin: `ParityQb_QB02_ArangeFloatOverloads_AreFloat64LikeNumPy`. Fix size: two lines (pass no dtype / float64), a
  breaking change for callers who relied on the float32 result.
- Added 02:08 (`q60`, `q61`): a C# `ulong` argument has no overload of its own and BINDS THE FLOAT ONE (C#'s better
  conversion picks `float` over `double`), so `np.arange(18446744073709551610UL, 18446744073709551615UL, 2UL)` is an
  EMPTY float32 array (both bounds round to the same float32) where NumPy's Python ints give three float64 elements
  (`[1.8446744073709552e+19] * 3`, the length computed exactly). Fixing QB-02 by deleting the float overloads would move
  `ulong` onto the `double` overload; NumPy's rule needs the exact integer length (a `ulong` / `BigInteger` path).

### QB-61 — a single ndarray passed to `vstack` / `hstack` / `column_stack` / `dstack` is NumPy's sequence of its rows (S1, silent wrong shape)

- Symptom (`q168`): with `M` a `(3, 2)` array and `v` a `(3,)` array, `np.hstack(M)` is `(3, 2)` here and `(6,)` in
  NumPy; `np.column_stack(M)` `(3, 2)` here, `(2, 3)` in NumPy (rows become columns); `np.dstack(M)` `(3, 2, 1)` here,
  `(1, 2, 3)` in NumPy; `np.vstack(v)` `(1, 3)` here, `(3, 1)` in NumPy (`np.column_stack(v)` `(1, 3)`, `np.dstack(v)`
  `(1, 1, 3)`). Same values, another shape and order, no error. `np.vstack(M)` happens to agree.
- NumPy: the stackers take a sequence of arrays, and an ndarray is a sequence of its first-axis slices.
- NumSharp: `params NDArray[] tup` wraps a lone NDArray into a one-element sequence, so each stacks the array itself.
  np.concatenate and np.stack take `NDArray[]` without `params`, so the same idiom (`np.concatenate(M)`, the row
  flatten; `np.stack(M)`) does not compile there (CS1503). numpy.ma's stackers (`params object[] tup`) inherit it
  (`q181`): `np.ma.hstack(masked (3, 2))` is `(3, 2)` here and `(6,)` in NumPy, `np.ma.column_stack` / `np.ma.dstack`
  likewise, and `np.ma.vstack` of a masked 1-D array is `(1, 2)` here, `(2, 1)` in NumPy. And so does
  `np.linalg.multi_dot(arrays)` (`q190`, its `params NDArray[]`): a stack of matrices passed as one 3-D array is the
  chain product in NumPy (`multi_dot(np.arange(8.).reshape(2, 2, 2))` is `[[6, 7], [26, 31]]`) and "Expecting at least
  two arrays." here; a `(2, 2)` array is the dot of its two rows in NumPy (11.0).
- Pin: `ParityQb_QB61_SingleArrayToTheStackers_IsASequenceOfRows`. Fix size: small (a single-NDArray overload that
  iterates the first axis, as NumPy's sequence protocol does; or refuse it).
