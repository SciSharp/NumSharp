# NumPy parity QA journey — 2026-11-08 / 09

A second deep manual QA pass over NumSharp, on branch `journey5` (base `e25b7522`), looking for behaviour that differs
from NumPy 2.4.2. It follows the first journey ([`parity-qa-2026-11-02.md`](parity-qa-2026-11-02.md), QA-01 … QA-55,
all decided) and aims at what that pass could not see: the code that landed after it (the parity batches 1–14
themselves, the subclass redesign, the np.dot / np.vecdot / np.vdot rewrites, the reduction and reversed-operand
kernels, the ufunc result-layout re-port, the Shape copy-keyword refactor, np.evaluate over text), and new techniques
(concurrency, guard pages, size thresholds, layout-invariance metamorphic checks, NumPy's own regression tests).

Every confirmed divergence gets an id (`QB-NN`), an entry below and an `[OpenBugs]` reproduction in
[`test/NumSharp.Tests/OpenBugs.ParityQb.cs`](../../test/NumSharp.Tests/OpenBugs.ParityQb.cs)
(`IssueUrl = "parity-qa-QBNN"`). Nothing found here is fixed in this pass: the owner decides which ones to fix.

- Window: 2026-11-08 22:58 → 2026-11-09 06:58 (local clock of the session, 8 hours).
- Method: a probe harness in the session scratchpad (`h/pq.py`): one probe file per direction, each line
  `name :: <C# expression> :: <NumPy expression>`; the runner generates and builds the C# side against an isolated
  journey5 worktree (Release), runs the NumPy side in process, and compares canonical results — dtype, shape, every
  element bit for bit (NaN-blind unless asked, signed zero kept), the C / F / writeable flags and the array class on
  request, error-versus-value, and the error type and text. Every reported difference is re-checked by hand before it

  `test/NumSharp.Tests.Oracle/Fuzz/README.md`, existing `[OpenBugs]` pins, a 0-d array where NumPy returns a scalar,
  the first journey's Observations) are not findings.
- Severity: **S1** silent wrong value / memory unsafety; **S2** crash or refusal where NumPy computes (or computes where
  NumPy refuses); **S3** wrong dtype / shape / layout / flags / class; **S4** error type or message text.

## Findings

### QB-01 — complex `np.sign` divides by np.absolute's magnitude instead of `npy_hypot` (S1, ULP-level)

- Symptom: `np.sign(np.array([-2+7j]))` is `-0.274721127897378+0.961523947640823j`; NumPy 2.4.2 gives
  `-0.27472112789737807+0.9615239476408232j`. Over 20,000 complex values with log-uniform magnitudes (1e-13 … 1e13
  per part), 4,552 (22.8 %) differ by 1–2 ULP in a part; `np.sign(1e-300+1e-300j)` too.
- NumPy: `CDOUBLE_sign` (`_core/src/umath/loops.c.src`) is `in1abs = npy_hypot(in1r, in1i)`, then the zero / NaN /
  infinity branches, then `(in1r / in1abs, in1i / in1abs)`. On win-amd64 `npy_hypot` is the UCRT `hypot`, which
  NumSharp already reproduces exactly (`NDHypotMath`, parity QA-25: `np.hypot` matched all 20,000 pairs here too).
- NumSharp: the complex branch of `DirectILKernelGenerator.EmitSignCall` (`DirectILKernelGenerator.Unary.Math.cs`)
  computes `NDComplexMath.Abs(z)` — np.absolute's SIMD formula `larger * sqrt(fma(ratio, ratio, 1))` — and divides by
  it (`Complex / double`, the same per-part division as NumPy). The zero / NaN / infinity branches are right.
  Computing `np.real(z) / np.hypot(re, im)` and `np.imag(z) / np.hypot(re, im)` with NumSharp's own kernels matches
  NumPy on all 20,000 values, so the fix is one helper call (`NDHypotMath`'s UCRT model in place of
  `NDComplexMath.Abs`).
- Why no gate caught it: `MisalignedRegistry`'s branch (6b) "complex unary within 3 ULP (full NumPy-algorithm port)"
  excuses every one-operand complex op not in `ByteExactArithmeticUnaryOps`; it was written for the transcendental
  `npy_c*` ports, and `sign` has no transcendental step. Adding `sign` to the byte-exact set would gate the fix.
- Pin: `ParityQb_QB01_ComplexSign_DividesByNpyHypot`. Fix size: one line (plus the registry entry).

### QB-02 — `np.arange`'s C# `float` overloads return float32 computed in float32 (S3 dtype, S1 values)

- Symptom: `np.arange(0f, 1f, 0.1f)` is a float32 array `[0, 0.1f, 0.2f, 0.30000001192092896f, …]`;
  `np.arange(3.5f)` is float32 `[0, 1, 2, 3]`.
- NumPy: arange never returns float32 without `dtype=`. `np.arange(np.float32(0), np.float32(1), np.float32(0.1))`
  and `np.arange(np.float32(3.5))` are float64, filled as `start + i*delta` in double (`[3]` is
  `0.30000000447034836`); a C# `float` read as the house map's Python float gives the same (the float32 value widened
  is the same double).
- NumSharp: `np.arange(float start, float stop, float step = 1)` (region "Original overloads (type inferred from C#
  parameter types)", `Creation/np.arange.cs`) calls `arange(start, stop, step, NPTypeCode.Single)`, and
  `arange(float stop)` forwards to it. The same region's int overloads already return NumPy's int64, and
  `np.linspace(0f, 1f, 5)` (the float overload of linspace) is float64, so the float arange is the one place where a C#
  `float` argument still decides the result dtype.
- Pin: `ParityQb_QB02_ArangeFloatOverloads_AreFloat64LikeNumPy`. Fix size: two lines (pass no dtype / float64), a
  breaking change for callers who relied on the float32 result.

### QB-03 — `np.repeat` with an array of counts: the negative-count text lacks NumPy's period (S4)

- Symptom: `np.repeat(a, np.array([1, -1, 2]))` raises `ArgumentException: repeats may not contain negative values`;
  NumPy 2.4.2 raises `ValueError: repeats may not contain negative values.` (`PyArray_Repeat`, `item_selection.c`).
- NumSharp: `UnmanagedStorage.ItemSelection.cs` (`ComputeCounts`, both the 1-D and the general branch) drops the period.
  The broadcast (single count) branch's different wording is documented (creation-manipulation.md: NumPy's text there
  is `negative dimensions are not allowed`), as is the scalar `np.repeat<T>(T a, long)` overload's.
- Pin: `ParityQb_QB03_RepeatNegativeCountArray_TextEndsWithPeriod`. Fix size: one character in two places.

### QB-04 — `item()` of an array whose size is not 1 does not raise ValueError (S4)

- Symptom: `np.arange(5).item()`, `item<long>()` and `np.zeros(0).item()` throw `IncorrectSizeException`;
  `np.ma.masked_array(np.arange(3.0)).item()` throws `InvalidOperationException`. Both carry NumPy's text.
- NumPy 2.4.2: `ValueError: can only convert an array of size 1 to a Python scalar` for ndarray and MaskedArray.
- NumSharp: `Manipulation/NDArray.item.cs` (both `item()` and `item<T>()`) and `Ma/NDMaskedArray.cs` (`item()`).
  `IncorrectSizeException` derives `NumSharpException`, not `ValueError`, so `catch (ValueError)` or
  `catch (ArgumentException)` misses it; NumSharp's own text arrays (`NDListArray.item`) already throw `ValueError`,
  as does `NDMaskedArray`'s scalar conversion path (line 555).
- Pin: `ParityQb_QB04_ItemOfANonSizeOneArray_RaisesValueError`. Fix size: three throw statements (and their
  `<exception>` docs).
- Caveat (found after pinning): the oracle's `FuzzCorpusTests.Kinds.ErrorTypeMap` names "ndarray.item's size guard … the
  house IncorrectSizeException" as an accepted counterpart of NumPy's ValueError, and accepts InvalidOperationException
  for ValueError / TypeError, so this is a house convention rather than an oversight. It stays a finding because the
  library is split on it (NDListArray and the masked scalar path throw `ValueError` with the same text), but it is the
  owner's call: see Open question 1.

### QB-05 — complex `log` / `log2` / `log10` / `arctan` / `arctanh` / `expm1` use stale private real `log1p` / `expm1` helpers (S1, ULP-level; up to 2,048 ULP in a cancelling part)

- Symptom (30,000 complex values, log-uniform magnitudes e^±8; expm1 over the square [-3, 3]²): log differs on 334
  (1 ULP), log2 / log10 on ~260–310 (≤ 2 ULP), arctan / arctanh on ~7,970 (≤ 2 ULP), expm1 on 1,487 (up to 2,048 ULP
  in the real part where `expm1(x)·cos(y)` and `2·sin²(y/2)` cancel). Examples: `np.log(-1.0571132398591-0.6968054066842436j)`
  real part `0.23594660164716705` (NumPy `…702`); `np.expm1(0.6364991061529732-0.6534557720485368j)` real part
  `0.500520053534724` (NumPy `0.5005200535347242`).
- NumPy: on win-amd64 `npy_config.h` blocklists MSVC's `clog` / `catan(h)`, so `nc_log` / `nc_atan(h)` run npymath's
  `npy_clog` (near |z| = 1: `npy_log1p((am-1)*(am+1)+an*an)/2`) and `npy_catanh` (`npy_log1p(4*ax/sum_squares(ax-1, ay))/4`);
  `nc_expm1` is `npy_expm1(x)*cos(y) - 2*sin²(y/2)`. `npy_log1p` / `npy_expm1` are the UCRT's.
- NumSharp: parity QA-22 made the real `np.log1p` / `np.expm1` the UCRT's exactly (`NDLog1pExpm1Math.Log1p` =
  `log(u) - ((u - 1) - x) / u`; `Expm1` = `exp(x) - 1` outside [-ln 2, ln 1.5], Sun's within 2 ULP inside), but
  `Utilities/NDComplexMath.cs` kept two private helpers from before it: `MathLog1p` (`log(w) * (u / (w - 1))`, used by
  `Log` and `Catanh`) and `RealExpm1` (`(e^x - 1) * x / log(e^x)`, used by `Expm1`).
- Proof the fix closes it: rebuilding NumPy's `npy_clog` from NumSharp's own exact real ufuncs (np.hypot, np.log1p, np.log,
  np.arctan2) matches NumPy's complex log on all 30,000 values (`q05`); a Python port of `npy_catanh` with the UCRT log1p
  model matches `np.arctanh` on all 30,000 (`h/casinh_port.py`). For expm1, 665 of the 1,487 differences lie outside
  the band, where the real model is exact; inside it the residual is QA-22's documented 2-ULP band.
- Why no gate caught it: the registry's "complex unary within 3 ULP" branch (6b) excuses them. float-math.md's section
  "The platform libm: `expm1` / `log1p`" still describes the pre-QA-22 `Exp(x)-1` / `Log(1+x)` state (stale).
- Also reached through np.emath (`d19`, 20,000 reals in [-50, 50] / [-3, 3]): `emath.log` / `log2` / `log10` / `logn` of
  negative reals near |x| = 1 (75–97 values), `emath.arctanh` (1,743), and every complex log near |z| = 1 (16.5 % of a
  [-1.2, 1.2] × 0.8j band).
- Pin: `ParityQb_QB05_ComplexLogAtanhExpm1_UseTheExactRealLog1pExpm1`. Fix size: replace two private helpers by calls to
  `NDLog1pExpm1Math` (plus tightening branch 6b for these ops).

### QB-06 — complex `arcsin` / `arccos` / `arcsinh` / `arccosh` compute through `System.Numerics.Complex`, not npymath's msun ports (S1, ULP-level, up to 5 ULP)

- Symptom (30,000 values as above): arcsin / arcsinh differ on 7,574 / 7,717 values, arccos / arccosh on 14,083, by
  1–5 ULP. Example: `np.arcsin(88.209178279867+909.9421975228022j)` real part `0.09663730993736097` (NumPy `…096`);
  `np.arccos(-5.686795079249146+243.19353968737j)` real part `1.5941756932192905` (NumPy `…908`).
- NumPy: `npy_config.h` blocklists MSVC's `casin` / `casinh` / `cacos` / `cacosh`, so NumPy runs npymath's msun ports
  (`npy_casinh` with `_do_hard_work`, `npy_casin` = `I·conj(casinh(I·conj z))`, `npy_cacos`, `npy_cacosh`), whose real
  steps are the UCRT hypot / log1p / sqrt / log / asin / atan2.
- NumSharp: `NDComplexMath.Asin` / `Acos` call `System.Numerics.Complex.Asin` / `Acos` for every finite input and only
  repair zero signs (the non-finite tables are ported); `Asinh` / `Acosh` derive from them. The code comments call them
  "byte-exact ports", and float-math.md says the same.
- Proof the fix closes it: a 60-line Python port of `npy_casinh` (`_do_hard_work`, `_f`) using `math.*` plus the UCRT
  hypot and log1p models NumSharp already has matches `np.arcsinh` and `np.arcsin` on all 30,000 values
  (`h/casinh_port.py`).
- Why no gate caught it: branch (6b) "complex unary within 3 ULP" — and the 4–5 ULP cases exceed even that, so the corpus
  holds none of them (branch (7) exempts arccos / arccosh, not arcsin / arcsinh).
- Also reached through np.emath (`d19`): `emath.arcsin` / `emath.arccos` of reals outside [-1, 1] differ on 2,123 /
  3,328 of 20,000 values in [-3, 3].
- Pin: `ParityQb_QB06_ComplexArcsinArccos_AreNpymathsMsunPorts`. Fix size: port `npy_casinh` / `_do_hard_work` (~120 C
  lines) and `npy_cacos` (~80), already half present as the non-finite tables.

### QB-07 — a binary or comparison result over a reversed / stepped C-ordered view and an F array is F-ordered (S3 layout; another `ravel('K')` order)

- Symptom: `np.add(m[::-1], np.asfortranarray(n))` (float64, 3 × 4) has strides `(8, 24)` (F); NumPy 2.4.2 gives
  `(32, 8)` (C). The same for subtract / multiply / true_divide / maximum, the `+` / `*` operators, `np.less` (bool,
  `(1, 3)` against `(4, 1)`), a stepped view (`x[:, ::2]`), any axis reversed, in 2-D and 3-D, in either operand
  order. `ravel('K')` / `flatten('K')` of the result read another element order (`[8, 8, 8, 10, …]` against NumPy's
  `[8, 10, 12, 14, …]`). Every dtype (bool, uint8, int32, int64, float16, float32, float64, complex128, a mixed
  int32 + float64 pair) and most binary ufuncs: add / subtract / multiply / true_divide / power / float_power /
  floor_divide / mod / fmod / fmax / gcd / left_shift / right_shift / bitwise_and / logical_and, the six comparisons and
  np.isclose (`q07c`). Not affected: arctan2, hypot, logaddexp, copysign, heaviside, nextafter, logical_xor, ldexp,
  np.where, np.clip and np.evaluate, whose routes lay out through the K-order plan only.
- NumPy: no trivial loop (the view is not contiguous), so NpyIter's K order lays the output out;
  `npyiter_find_best_axis_ordering` compares |strides| per operand and C order wins any conflict, so a C-ordered
  view against an F array gives C.
- NumSharp: the route's K-order step (`MayNeedKOrder` / `IsKOrderCVoter`, which counts a reversed or stepped C-ordered
  view as a C voter) gets C, but the float64 binary routes (`DefaultEngine.BinaryOp.cs`, both the direct and the
  Tier-3B route) and the comparison routes (`DefaultEngine.CompareOp.cs`) then run the legacy "looser-F
  preservation" step: `ShouldProduceFContigOutput` returns true when some operand is strictly F and none strictly C,
  and the result is copied to F (`result.copy('F')`). A non-contiguous view is neither, so it does not vote. The fix is
  to drop that step where the K-order plan has run, or to make it `IsKOrderCVoter`-aware; it also removes a copy.
- Pin: `ParityQb_QB07_BinaryOfAReversedViewAndAnFArray_IsCOrdered`. Fix size: small (two routes × two call sites).

### QB-08 — zero-size results the allocation-strides fix does not reach (S3, `strides` only)

- Symptom: `np.full_like(np.zeros((2, 0, 4)), 7.0)` has strides `(0, 32, 8)` and `np.unique` of an empty array `(8,)`,
  where NumPy 2.4.2 allocates both with all-zero strides (`(0, 0, 0)`, `(0,)`); `np.array(new double[0, 3])` (a C# array)
  is `(24, 8)` where NumPy's allocation of the same zero-size array is `(0, 0)`. The reverse where NumPy's result is a
  reshaped view: `np.tile(np.arange(3), 0)` and `np.fromstring("", sep=" ")` are `(8,)` in NumPy and `(0,)` in NumSharp.
- NumPy: `PyArray_NewFromDescr_int` zeroes every stride of a zero-size allocation; a view keeps the strides its
  reshape / slicing computed.
- NumSharp: the ufunc result-layout re-port (`18314cac`, today) routed every allocator through
  `Shape.ForFreshAllocation` and closed the allocation half of `OpenBugs.EmptyStrides.cs` ("every fresh zero-size
  allocation gets all-zero strides"); np.full_like, np.unique's empty result and the C#-array constructor still build
  their shape without it, and np.tile / np.fromstring allocate where NumPy reshapes. The other 44 producers in `q10`
  match.
- Pin: `ParityQb_QB08_ZeroSizeResults_TakeNumPysStrides`. Fix size: small per site (route through the funnel; keep the
  view in tile / fromstring).

### QB-09 — `np.matmul` (and 2-D row · column `np.dot`) keep another NaN than NumPy (S1, NaN sign / payload)

- Symptom: `np.signbit(np.matmul([-nan, 1.0], [1.0, nan]))` is False; NumPy 2.4.2 gives True (its result is the first
  operand's `-nan`). The same for `np.matmul(a.reshape(1, 2), b.reshape(2, 1))`, the `@`-style matmul of NDArrays and
  `np.dot` of those 2-D shapes. With distinct NaN payloads per operand, matmul 1-D @ 1-D, 1-D @ 2-D, 2-D @ 1-D,
  (1, n) @ (n, 1), (1, n) @ (n, 2), (2, n) @ (n, 2) and 2-D np.dot keep another payload than NumPy; (2, n) @ (n, 1)
  (NumPy's gemv) and einsum `ij,jk->ik` match.
- NumPy: `cblas_matrixproduct` / matmul's inner loop call the dtype's dot function (cblas `ddot`) for a vector-vector
  product and a 1 × 1 output; that ddot keeps the first operand's NaN here, as NumSharp's 1-D `np.dot` already does
  (parity PA3b, `95191628`: "which NaN survives where several meet is NumPy's across np.dot / np.vdot / np.vecdot").
- NumSharp: np.matmul and the 2-D np.dot route through the managed GEMM / matmul kernels, which accumulate in their own
  order, so the surviving NaN is another one; PA3b did not cover them. Routing the shapes NumPy hands to ddot (two
  vectors, a row times a column, a 1 × 1 output) to the PA3b dot would close the visible half; GEMM-shaped products are
  BLAS-blocking-dependent in NumPy too.
- Pin: `ParityQb_QB09_MatmulOfVectors_KeepsNumPysNaN` (np.dot asserted as the control). Fix size: small for the vector
  shapes.

## Observations (not pinned)

Differences seen and judged not to be findings, with the reason.

- numpy.matrix operands (`d02`): `np.vdot(m, m)` is NumPy's `matrix([[1.]])` (array_vdot's `PyArray_Newshape(-1)`
  keeps the matrix 1 × 6, so it dots one element), `np.concatenate((m, m), axis=None)` raises NumPy's own
  "cannot copy from array of size 6 into an array of size 72", `np.lexsort(m)` is NumPy's `(1, 3)` (the sequence
  protocol hands it 1 × 3 rows), `np.roll(m, 1)` without an axis leaves NumPy's matrix unchanged, `np.append(m, m)`
  without an axis raises: NumPy's matrix semantics leaking into its own code (gaps MO02 – MO05 cover most of them by
  name; `np.concatenate(axis=None)` and `np.lexsort` are two more of the same kind). NumSharp returns the values of the
  plain call. `np.any(m, 0)` binds the typed `NDArray<bool> any(NDArray, int, bool)` overload and returns a plain `(3,)`
  where NumPy's `matrix.any` gives a `(1, 3)` matrix: the documented "typed return cannot carry the class" limit, but
  matrix.md's sentence "the typed np.all / np.any overloads … are plain in NumPy too" is wrong for an axis (worth a doc
  fix).
- `np.cov(m)` / `np.corrcoef(m)` of a 2 × 3 float64 matrix differ by 1 ULP: the managed Gram path, documented
  (reductions.md "cov is GEMM-bound").
- complex `np.sin` / `np.tanh` differ by 1 ULP on some inputs (`d05`): inside the documented 3-ULP envelope of the
  complex unary ports (registry branch 6b). Measured at scale (`d09`, [-3, 3]²): sin / cos / sinh / cosh differ on ~46 %
  of inputs, tan / tanh on ~30 %, all ≤ 3 ULP. These are NOT blocklisted on MSVC, so NumPy calls the UCRT's `csin` /
  `ccos` / `csinh` / `ccosh` / `ctan` / `ctanh`; the textbook formulas over the UCRT reals (and five variants) do not
  reproduce them (only `cexp` is the textbook `exp(x)·cos(y)`, which NumSharp matches exactly). Not a finding (documented
  envelope), but the root CLAUDE.md sentence "complex128 … its unary ufuncs match NumPy bit for bit" overstates: the
  NaN-sign contract is exact, the finite values are not.
- `np.concatenate(..., dtype=np.int32)` of float64 with `same_kind` raises `InvalidCastException` with NumPy's text
  (NumPy: TypeError): the house convention for cast refusals outside the ufuncs (np.copyto documents it).
- AxisError texts carry .NET's `(Parameter 'axis')` / `Actual value was N.` decoration: documented.
- `np.arange(10, dtype='>f8')` returns native float64: the documented "no non-native storage" divergence.
- `np.finfo(np.float32).eps` is a C# `double` (NumPy: `np.float32`): the typed-field design of `finfo`.
- `np.sum(a, axis=(0, 2))`: NumSharp reductions take one axis (documented "no tuple axes").
- Stale oracle excuses (a gate hazard, not a parity bug): `MisalignedRegistry` still carries "[known bug]" branches
  whose bugs no longer reproduce in `d10` — int floor / ceil / square / trunc widening (F3b), the float16 hyperbolic /
  inverse-trig / angle refusal, repeat of offset / 0-d views, power uint64 × int64 and float16 widening, empty
  nan-reductions throwing, nanmedian propagating NaN, float16 / int modf, expand_dims / atleast_3d of empty arrays,
  int8 dot, bool min / max along an axis, axis max / min skipping NaN, mixed signed / unsigned result_type with a 0-d
  operand. Each still excuses any case it matches, so a regression of those paths would pass the gate silently;
  removing the branches (after an unfiltered oracle run confirms none fires) would close that. The isscalar(0-d)
  branch is labelled "[known bug]" although `np.isscalar`'s docs make a 0-d NDArray a scalar on purpose.
- Latent, not reachable from the public API (`q08`): the element-reduction ArgMax / ArgMin kernel for complex128
  (`DirectILKernelGenerator.Reduction.Arg.cs`, `ArgMaxComplexHelper` / `ArgMinComplexHelper`) compares MAGNITUDES and its
  comment says NumPy does; NumPy orders complex lexicographically (real, then imaginary). Every public route (np.argmax /
  argmin flat and per axis, keepdims, out=, ndarray / typed / matrix / masked members, nanargmax / nanargmin,
  np.evaluate's ArgMax / ArgMin, 17-repeat inputs) answers lexicographically and matches NumPy, so the helper is dead or
  shadowed; a future route to it would be silently wrong.
- `NDPolyBase.Algebra`'s CPython `complex ** int` emulation (n > 100, polar form) uses .NET's `double.Hypot` where CPython
  calls the UCRT hypot (which NumSharp models exactly in `NDHypotMath`); geomspace's complex `out_sign` divides by
  `Complex.Abs`. Both sit inside documented ≤ 3-ULP complex envelopes; noted as the QB-01 / QB-05 pattern.
- `np.round` does not exist (only `np.round_` / `np.around`): documented in `coverage/overrides.json` (NumPy 2.0
  removed `np.round_`; `np.round` is its 2.x name).
