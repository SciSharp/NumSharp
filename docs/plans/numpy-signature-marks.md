# NumSharp `np.*` names marked against NumPy 2.4.2

Generated by `tools/api-parameter-parity/signature_diff.py` (4th argument) from the same comparison as
[`numpy-signature-diff.md`](numpy-signature-diff.md). Do not edit it by hand. Every C# name of every
`[ModuleName]` module, of `np.random.Generator` and (with `--types`) of every object API (`np.ma.MaskedArray`,
`np.matrix`, `np.char.chararray`, `np.dtype`, `np.nditer`, the bit generators, ...) is listed once, NumPy's names
first, then the names NumPy does not have. Constructors are the row `(constructor)` (NumPy's class call). The
marks look at ALL overloads of a name together (extension methods included). What each mark means for a port,
how to fix it, and every affected name grouped by fix: [`API_DIFF_GAP.md`](API_DIFF_GAP.md).

| mark | meaning |
|---|---|
| **M** ● | NumSharp is missing a NumPy parameter: no overload offers it. A rename counts, because NumPy's keyword does not compile: `axes (C#: premute)` |
| **M** ◦ | only parameters the parity plan excludes are missing (`like`, `subok`, a ufunc's `casting` / `order` / `signature`, the field `order` of the sorts, `einsum_call`) |
| **X** ● | NumSharp has a parameter NumPy does not have, in at least one overload (names at a positional-only slot, C# spellings of `*args`, and keywords NumPy takes through `**kwargs` are not counted) |
| **O** n | the name has n C# overloads, where NumPy has one signature |
| **T** ● | an overload takes a dtype as `NPTypeCode` or `Type` (nullable and array forms included) instead of `DType` |
| **T** ◇ | a generic overload whose type argument picks the dtype (`iinfo<T>()`): the caller names a CLR type instead of a `DType` |
| **B** ● | a NumPy-style call does not compile: the required parameters alone, the optional positional ones positionally in NumPy's order, one optional parameter alone (it binds only together with another one), the dtype as a string (`dtype: "float64"`), several values where NumPy takes `*args` (`a.transpose(1, 0)`), the call without a parameter NumPy leaves unset (`np.ma.where(condition)`), or all NumPy parameters in one call (they are split across overloads, or the overloads tie) |
| **B** ◐ | such a call compiles at the latest C# but not at C# 12, a net8.0 consumer's default: it relies on `[OverloadResolutionPriority]`, which C# 12 ignores |
| **L** ● | passing `null` where NumPy's default is None does not compile (a value-type parameter, or two overloads `null` fits equally well) |
| **L** ◐ | the same at C# 12 only (`[OverloadResolutionPriority]`) |
| **L** ◦ | only `Shape` parameters refuse `null`, and `default` (NumSharp's spelling of `size=None`) binds |
| **Q** ● | NumPy's stubs let a parameter take a sequence of integers (`axis=(0, 1)`, `size=(2, 3)`), and neither `new[] { 0, 1 }` nor the tuple `(0, 1)` binds there |
| — | not applicable: NumPy states no signature for the name, or NumPy has no such name |

Matching: positional-only NumPy parameters by slot, the others by name. `*args` is offered by a `params`
array or by C# parameters at its slot. NumPy's parameters come from its runtime signature; where that signature
forwards `(*args, **kwargs)`, the parameters it hides are added from NumPy's type stubs (`.pyi`) and the
numpydoc `Parameters` section, shown as `+ name (stub)` / `+ name (doc)` under the signature. The column *missing
on NumSharp* lists the M parameters (excluded ones after `excluded:`), *NumSharp-only parameters* the X ones,
*NPTypeCode / Type* the T parameters (an NPTypeCode / Type return type, and the generic `<T>` overloads).

B, L and Q come from `binding_probe.py`, which writes NumPy-style calls of every compared name and compiles
them against NumSharp at C# 12 and at the latest C#: the required parameters only (`np.sum(a)`), the optional
positional ones positionally in NumPy's order (`np.sum(a, 1, np.float64)`), each optional parameter alone by
name with an ordinary value (`np.empty(shape, device: "x")`) and, where NumPy's default is None, with `null`
(and `default` for a `Shape`), every NumPy parameter in one call with NumPy's defaults (and again with ordinary
values where those are None), a sequence where the stubs allow one, the dtype as a string, several values at
NumPy's `*args` (`a.transpose(1, 0)`, `np.meshgrid(x, y, z)`), and the call without the parameters NumPy marks
"not passed" where every overload requires them (`np.ma.where(condition)`; not `np.vectorize()`, NumPy's
decorator form). A failure already explained by a smaller call is not repeated. The column *compile probe*
lists what failed, with the compiler's reason.
