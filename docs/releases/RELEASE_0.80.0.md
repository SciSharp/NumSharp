# NumSharp 0.80.0

We are at 95.2% NumPy API coverage, and everything except datetime, complex64 and other exotic dtypes matches NumPy byte for byte.
This release brings NumPy's text dtypes with numpy.strings and numpy.char, numpy.ma, numpy.polynomial, np.emath and 48 new np.* functions.
Integration rather than competition goes on, this time inside .NET: an NDArray now runs through ONNX Runtime models, serves as an ML.NET IDataView and shares its memory with System.Numerics.Tensors.

### 🧭 Overview
- NumPy 2.x API coverage around 95.2%, everything except datetime, complex64 and other exotic dtypes is fully supported, with byte-to-byte equality and compatibility to NumPy.
  - Text - NumPy's fixed-width `bytes_` (`S`) and `str_` (`U`) dtypes and NEP 55's variable-width `StringDType`, with every computation NumPy runs on text, all **46** `numpy.strings` functions and `numpy.char` with `chararray`.
  - `np.polynomial.*` - the whole `numpy.polynomial` package, **all 193 functions and the six series classes** for all six bases, bit-exact.
  - `np.*` - **+48 functions**, the ten most used on GitHub: `np.hypot`, `np.histogram`, `np.logspace`, `np.gradient`, `np.vectorize`, `np.hanning`, `np.geomspace`, `np.apply_along_axis`, `np.trapezoid` and `np.histogram2d`.
  - `np.random.*` - every NumPy bit generator, the whole `Generator` distribution surface, and a legacy `RandomState` that is NumPy's own sampler code line for line, all byte-identical streams.
  - `np.ma.*` - the masked-array module; `np.emath.*` - the automatic-domain math module; `np.matrix` - `numpy.matrix` as the new `NDMatrix` type.
- **`DType` is NumPy's two-level dtype model** - `NDArray.dtype` returns a `numpy.dtype`-shaped descriptor, with `np.dtypes`, byte order and `datetime64` / `timedelta64` descriptors, and NumPy's scalar classes (`np.integer`, `np.floating`, `np.number`, ...) with `np.typing`.
- **Reductions on NumPy's own schedules** - `max`, `min`, `ptp`, `nanmax`, `nanmin`, `argmax`, the flat `sum` / `mean` and the fused `np.evaluate` reductions match NumPy bit for bit, down to the sign of a ±0 tie and a NaN's payload; `mean`, `var`, `std` and their NaN-aware forms are NumPy's own statements; and most of them run faster.
- **NumPy's structure for the engine** - every computing `np.*` function is a `TensorEngine` member named after its NumPy source file, `numpy.linalg` and `numpy.fft` are replaceable sub-engines, and the default engine is settable.
- **The 2026-11-02 parity QA** - 53 of its 55 findings fixed on the owner's decisions (one kept as a documented divergence, one deferred), and NumPy's own dot functions behind `np.dot` / `np.vdot` / `np.vecdot`.
- **86 NumPy-parity, memory-safety and tooling fixes**, **40 measured speedups** and **44 breaking changes**, across the release's 1,670 commits.
- **3 new NuGet packages** - **NumSharp.Interop.System.Numerics.Tensors**, **NumSharp.Interop.OnnxRuntime** and **NumSharp.Interop.MLNet**.
- **1,119,305 NumPy 2.4.2 oracle test cases** (0.70.0: 119,517) and 20,506 test methods (0.70.0: 14,416).

### 📦 New NuGet Packages
- **NumSharp.Interop.System.Numerics.Tensors** - zero-copy interop between `NDArray` and the BCL's `Tensor<T>` / `TensorSpan<T>` ([System.Numerics.Tensors](https://www.nuget.org/packages/System.Numerics.Tensors)), all 15 dtypes.
- **NumSharp.Interop.OnnxRuntime** - run [ONNX Runtime](https://onnxruntime.ai) models on `NDArray`s, fed from the arrays' own memory, with the outputs read back as `NDArray`s.
- **NumSharp.Interop.MLNet** - an `NDArray` as an [ML.NET](https://dotnet.microsoft.com/apps/machinelearning-ai/ml-dotnet) `IDataView`, and a transformer's output column back as an `NDArray`.

### 📦 New NuGet Packages

Three optional companion packages ship for the first time, co-versioned with **NumSharp** (each depends on **NumSharp**). None computes NumSharp operations: each converts arrays between NumSharp and another library, with no engine backend and no native asset of its own, so Core stays 100% managed without them.

- **NumSharp.Interop.System.Numerics.Tensors** - zero-copy interop between `NDArray` and [System.Numerics.Tensors](https://www.nuget.org/packages/System.Numerics.Tensors) (`Tensor<T>`, `TensorSpan<T>`, `ReadOnlyTensorSpan<T>`); all 15 NumSharp dtypes cross as their own CLR type, `Half`, `Complex`, `decimal` and `char` included.
  - Export - `AsTensorSpan<T>()` views an `NDArray` of any non-negative-stride layout (contiguous, sliced, transposed, strided, broadcast) as a `TensorSpan<T>` over the same unmanaged buffer, through a disposable handle that keeps the buffer pinned; `ToTensor<T>()` copies into a dense `Tensor<T>`.
  - Import - `AsNDArray()` views a `Tensor<T>` as an `NDArray` without copying (writes go through to the tensor, and the pinned array counts toward NumSharp's memory accounting until the last view is disposed); `ToNDArray()` copies a `Tensor<T>`, `TensorSpan<T>` or `ReadOnlyTensorSpan<T>`.
  - Text - `S` / `U` / `StringDType` arrays cross as a `Tensor<string>` copy in both directions (`ToStringTensor()` / `ToNDArray(Tensor<string>)`); the view verbs refuse text with one message, because a `Tensor<string>` holds managed strings.
  - The exported spans feed the BCL's SIMD `TensorPrimitives` directly, with no fill loop.
  - Limits - a negative-stride view is refused, because the BCL forbids negative strides (copy it first); the copies stop at the managed-array size limit; live export and import counters help leak checks.
  - Depends - [System.Numerics.Tensors](https://www.nuget.org/packages/System.Numerics.Tensors) 10.x only, a managed BCL package. Its tensor types are experimental, so the bridge marks its own API experimental too and you opt in once. No engine backend and no native asset: Core stays 100% managed.
- **NumSharp.Interop.OnnxRuntime** - feed an `NDArray` to an [ONNX Runtime](https://onnxruntime.ai) `InferenceSession` from the array's own memory and read the outputs back as `NDArray`s; no Python.
  - Modes - every entry that can share memory takes `Auto` (a view when ONNX Runtime can read the buffer in place, else a copy the handle owns), `View` (refuses to copy) or `Copy`.
  - Export - `AsOrtValue` / `ToOrtValue`, and `AsDenseTensor` / `ToDenseTensor` for ONNX Runtime's legacy tensor tier; import - `ToNDArray` copies (a legacy `Tensor<T>` too), `AsNDArray` views and can own the value.
  - Running a model - `session.Run(...)` binds the inputs by the model's names, checks each dtype with NumPy's casting rules and each declared shape, and refuses a missing required input (with onnxruntime's own message) or an unknown output name before the run; `RunInto` fills pre-allocated outputs; `RunAsync` / `RunIntoAsync` run ONNX Runtime's asynchronous inference (1.30.0 or later) and size a dynamic dimension (`batch_size`, `N`) from the fed inputs; the outputs of `Run` and `RunAsync` leave an `NDScope` (`scope.ReturnsTask(session.RunAsync(...))`).
  - Threads and disposal - every `OrtValue` the bridge touches is released once, after its last use: a `Dispose` from any thread, during a verb or while views of the value live, neither crashes nor hands out another value's data, and a disposed session or value is refused with `ObjectDisposedException`; `NDInferenceSession`, an `InferenceSession` with ONNX Runtime's constructors, releases a session once, after the bridge's runs on it.
  - Memory - `ToOrtValue`'s copy and every view the bridge hands out count toward NumSharp's memory accounting, so forgotten ones get collected: 5,000 forgotten `ToOrtValue` copies of a 602 KB array peak at +68 MB instead of +2,898 MB.
  - Text and non-tensor values - fixed-width `U` / `S` arrays cross as string tensors (a copy; `ReadStringTensor` reads one as `string[]`), and a `StringDType` array is refused with its sized-`U` remedy; `ToNDArrays`, `ToMap`, `ToMaps` and `GetMapKeys` read sequence and map outputs.
  - Post-processing - `Softmax`, `LogSoftmax`, `Sigmoid`, `Argmax`, `TopK`.
  - Dtypes - 12 cross without a copy, float16 by bit reinterpretation; `char` exports as uint16 and `decimal` as float64 through a copy the handle owns; complex and bfloat16 are refused, each refusal naming the route that works.
  - Depends - [Microsoft.ML.OnnxRuntime.Managed](https://www.nuget.org/packages/Microsoft.ML.OnnxRuntime.Managed) 1.16.0 or later, the C# API only: ONNX Runtime's native flavours exclude each other, so you reference the one you run. Verified on 1.16.0 and 1.31.1.
- **NumSharp.Interop.MLNet** - expose an `NDArray` to an [ML.NET](https://dotnet.microsoft.com/apps/machinelearning-ai/ml-dotnet) pipeline as an `IDataView` and read a transformer's output column back as an `NDArray`, with no POCO class and no row-by-row fill.
  - Export - `AsDataView` is a lazy `IDataView` over the buffer's strides (one vector column, or one scalar column per feature, a repeated name refused); `ToDataView` takes a snapshot; `ToVBuffer` copies into a `VBuffer<T>`.
  - Tables - `AsDataView` of a dictionary of named arrays is one view with a column per array, each in its own dtype (`{"Features": X, "Label": y}`, as pandas' `DataFrame`), so a model trains and scores from arrays with no `hstack` and no conversion step.
  - Shuffling - a view reports `CanShuffle` and walks a full permutation of its rows when a trainer asks for a shuffled cursor, so SDCA trained on class-ordered rows passes 0.65 accuracy (ML.NET's pool shuffle left it at 0.50).
  - Import - `ToNDArray` reads a scalar column as `(R,)` and a fixed-size vector column as `(R, C)`; `AsNDArray` views a dense `VBuffer<T>`'s array without copying, and the pinned array counts toward NumSharp's memory accounting until the last view is disposed.
  - Feeding a model - `transformer.Transform(nd.AsDataView("Features")).ToNDArray("Score")`: the `IDataView` is the whole bridge.
  - Post-processing - the ONNX Runtime bridge's `Postprocess` (`Softmax`, `LogSoftmax`, `Sigmoid`, `Argmax`, `TopK`), which this package references, so an app that uses both bridges has one.
  - Dtypes - 11 column types directly, `char` one way as uint16, float16 as float32 and `decimal` as float64 through a copy the view owns; complex and text arrays are refused, and a text, time or ragged column's refusal names the ML.NET route that reads it (`GetColumn<string>`, int64 ticks, `GetColumn<T[]>`).
  - Depends - [Microsoft.ML.DataView](https://www.nuget.org/packages/Microsoft.ML.DataView) 2.0.0 or later, and NumSharp.Interop.OnnxRuntime for `Postprocess` (bringing ONNX Runtime's C# API, which `Postprocess` never loads); the `Microsoft.ML` you reference brings the trainers and transforms. Verified on ML.NET 2.0.1 and 5.0.1.

### 🎯 Parity & Fixes
- `np.max` / `np.min` / `np.ptp`, flat and along an axis, run NumPy's own reduction schedules - the sign of a ±0 tie and a canonical-vs-payload NaN now match on every non-broadcast layout.
- `np.nanmax` / `np.nanmin` are NumPy's `fmax.reduce` / `fmin.reduce` bit for bit: complex128 skips NaN (it propagated it), float16 on non-C layouts read the wrong elements, and an all-NaN float16 slice returns its first NaN.
- complex128 arithmetic bit-exact with NumPy - `divide` (1 ULP off on ~33% of operands), `multiply` (NumPy's fused `simd_cmul`), `power` with an integer exponent (up to ~1e14 ULP off) and `abs` (NumPy's fused `simd_cabsolute`; 35.5% of values were off).
- The quantile family - `percentile` / `quantile` / `median` are NumPy's two-branch `_lerp` in each dtype's arithmetic (`median` the mean of the middle pair, a view at a non-zero offset read from its own start), the arguments are checked in NumPy's order, `q` follows NumPy 2.4.2 (an int `q` picks the element, a 2-D `q`, arithmetic in `q`'s dtype), the nan forms return NumPy's axis order and positive NaN, complex `median` of data holding a NaN returns the element NumPy's complex order puts last (`_median_nancheck`), and uint64 rounds once on .NET 8.
- `np.round` / `np.around` with `decimals != 0` port `PyArray_Round` - negative decimals threw, complex values stayed unrounded, float32 rounded in double, and the result dtypes follow NumPy.
- `sum` / `prod` of a size-0 or size-1 array widen the accumulator by NEP 50 like any other size.
- `np.array_equal(a, a)` with a NaN in `a` returned `True`; NumPy returns `False` unless `equal_nan`.
- int64-vs-uint64 comparisons are exact on every path (they went through float64).
- float16 `mod` / `floor_divide` / `fmod` by zero give ±inf like NumPy (they gave NaN), and float16 `add` / `subtract` / `multiply` / `divide` on the `out=` / `where=` / strided paths compute in float32 like NumPy's HALF loops (they double-rounded through double).
- float16 signalling NaNs stay signalling across every float16 cast route, uint64 at or above 2^63 converts to float64/float32 with one rounding on .NET 8 (it rounded twice, inside mixed uint64/float arithmetic and comparisons too), and `maximum` / `minimum` of float16 with float32/float64 keep the NaN's bits.
- `np.linalg.eig` / `eigvals` of a float32 matrix with complex eigenvalues return NumPy's complex64 values (they kept double precision).
- Use-after-free fixed: `np.real` / `np.imag` / `.real` / `.imag`, `view(dtype)` and `getfield` did not keep their owner's buffer alive, so after the owner was disposed (as inside `eigvals`) the next allocation overwrote them; `resize(refcheck: true)` now sees such views.
- `np.convolve` / `np.correlate` without the backend are byte-exact on float32 positions under 32 terms and complex128 positions under 8 (NumPy's scalar `sdot` / `zdotu` regimes), and complex products with inf/NaN follow NumPy (`convolve([1+0j], [inf+0j])` is `nan+nanj`).
- `np.arctan2(complex)` corrupted the heap and crashed the process; it raises NumPy's `TypeError`.
- `np.dtype(str)` follows NumPy's parser where it differed: `'cdouble'` and the intp letters `'n'` / `'N'` parse, a single control character is a type number (`'\x0c'` is float64), only C whitespace counts inside a sized code (`'f\xa08'` was accepted), and error texts quote the string like Python's `repr` (`data type "a'b" not understood`).

### 💥 Breaking Changes
- `DType` replaces `System.Type` as the dtype currency.
  - `NDArray.dtype` returns `DType` (was `Type`), and `np.float64`, `np.int32` and the rest are `DType` descriptors (were `Type`); `DType` -> `Type` is explicit (`a.dtype.type`), and `a.dtype.Name` is `a.dtype.name`.
  - Each dtype parameter takes one `DType`: the `Type` / `NPTypeCode` twins are gone (a `Type`, `NPTypeCode` or dtype string still converts implicitly), and `linspace` / `nancumsum`'s `typeCode:` is `dtype:`.
  - The promotion family (`result_type`, `promote_types`, `find_common_type`, `common_type`, ...) returns `DType`, and `isdtype` rejects `issubdtype`'s vocabulary (`"floating"`), as NumPy does.
- `finfo.dtype` / `iinfo.dtype` return `DType` (were `NPTypeCode`), and the pythonnet dtype maps take `DType`.
- `np.issubdtype`'s string argument is a dtype string, as in NumPy: the category names are gone (`np.issubdtype(x, "integer")` raises `data type 'integer' not understood`, and `np.issubdtype(np.float32, "float")` is False because `"float"` is float64); pass the class, `np.issubdtype(x, np.integer)`.
- Casting-rule strings are case-sensitive like NumPy (`"Safe"` raises `ValueError`).
- A byte-order prefix before a dtype NAME is refused, as in NumPy, which looks names up by the whole string: `np.dtype("<float64")`, `np.dtype("|bool")` and NumSharp's own `"<Int32"` raise `data type '<float64' not understood` (they were accepted). Before a code the prefix still works (`"<f8"`, `">i4"`).
- On Windows, `np.int32` / `np.int64` report the local NumPy's LLP64 type numbers and chars (`7` / `'l'` and `9` / `'q'`; they were hard-coded to Linux's `5` / `'i'` and `7` / `'l'`).
- `NPY_TYPECHAR` is NumPy 2.4.2's: `NPY_STRINGLTR2` is `NPY_DEPRECATED_STRINGLTR2`, `NPY_INTPLTR` / `NPY_UINTPLTR` are gone (cast the character, `(NPY_TYPECHAR)'n'`), and `NPY_VSTRINGLTR` (`'T'`) is new. `NPTypeCode.ToTypeCode(NPY_TYPECHAR)` reads a character as `np.dtype` does: `'D'` is complex128 (it was float64), `'l'` is int32 on Windows (it was int64), and `'F'`, `'S'`, `'U'`, `'V'`, `'c'` and the kind letter `'u'` are refused (they read as float32, char, char, `Empty`, complex and uint64). `ToTYPECHAR` gives the dtype's own character (`'D'` for complex128, it was `'c'`; `'q'` for int64 on Windows) and refuses decimal and char (they gave `'q'` and `'c'`), and their `dtype.char` is `'A'` / `'u'`, characters of their own that `np.dtype` refuses as NumPy refuses a user dtype's (they were int64's `'q'` and S1's `'c'`, so `np.dtype(d.char)` built another dtype).
- A write to a read-only array raises NumPy's `ValueError` (was `NumSharpException`); it derives from `ArgumentException`, so `catch (NumSharpException)` no longer catches it.
- `np.maximum` / `np.minimum` / `np.fmax` / `np.fmin` take `out` as the third positional argument (NumPy's order), not `dtype`; pass `dtype:` by name.
- `np.logical_and` / `logical_or` / `logical_xor` / `logical_not` return `NDArray` (was `NDArray<bool>`), and `np.modf`'s tuple field `Intergral` is `Integral`.
- `ndarray.shape = ...` raises NumPy's `AttributeError` when the layout cannot be reshaped in place (it silently copied); use `reshape`.
- `np.nanmax` / `np.nanmin` of an empty reduction raise NumPy's "zero-size array to reduction operation fmax which has no identity" (they returned a 0-d NaN).
- `new MT19937(42)` seeds like NumPy's `np.random.MT19937(42)` (through `SeedSequence`), not like `RandomState(42)`; `mt._legacy_seeding(42)` is the old stream. `MT19937`'s non-NumPy members (`NextUInt32`, `NextDouble`, `NextInt`, `NextLong`, `Next`, `NextBytes`, `Seed`, `SeedByArray`, `SetState`, `Key`, `Pos`, `Clone`) are gone, and `Pcg64StateData` is `PCG64.State`.
- Seeded legacy `RandomState` streams of `gamma(shape<1)`, `binomial`, `negative_binomial`, `poisson`, `f`, `pareto`, `power`, `standard_cauchy`, `multinomial`, `hypergeometric`, `zipf`, `geometric`, `vonmises` (and `gumbel` / `logistic` / `rayleigh` at scale 0) change to NumPy's values; `binomial(int n)` is `binomial(long n)`; inputs NumPy accepts (`dirichlet([])`, a NaN alpha, `negative_binomial(p: 0)`) no longer throw.
- Legacy integers are NumPy's LP64 C `long`: `randint` defaults to int64 (was int32), `random_integers` / `permutation` / `choice` / `multinomial` return int64, `NumPyRandom.Seed` is a `uint` (was `int`), and `SeedSequence.generate_state` returns an `NDArray` (was `Array`).
- NumPy's parameter names: `Generator(bit_generator)` (was `bitGenerator`), `PCG64(seed)` and the other bit generators (was `seedSeq`, now any `ISeedSequence`), and `default_rng(seed)` (was `bitGenerator` / `generator`) - named-argument calls must be renamed.
- The non-NumPy `NumPyRandom.uniform(NDArray low, NDArray high, DType dtype)` is removed; two-array calls bind NumPy's broadcasting overload (float64; `.astype()` the result for another dtype).
- `np.asmatrix` / `np.bmat` return `NDMatrix` (was a plain 2-D `NDArray`): `*` is the matrix product, an index keeps two axes, and `np.*` functions return NumPy's matrix results for it (`np.sum(m, 0)` has shape `(1, N)`); take `.A` for the plain array.
- An index-array assignment follows NumPy's value rule: a value that does not fit raises `ValueError` "shape mismatch: value array of shape (1,4) could not be broadcast to indexing result of shape (2,)" before anything is written (was `IncorrectShapeException`), and a `(1, N)` value now fits an `(N,)` selection.
- A boolean-mask assignment takes a 0-d or 1-d value: a 2-d value raises NumPy's `TypeError`, and a 1-d value whose length is neither 1 nor the number of true elements raises NumPy's `ValueError`.
- `Shape` is immutable and the shape accessors return copies, as NumPy's tuples are: the `Shape` indexer has no setter (`s[i] = v` no longer compiles; build a new `Shape`), `a.shape`, `Shape.Dimensions` and `Shape.Strides` return a copy on every read, and `new Shape(long[])`, `(Shape)long[]` and every public method taking a `long[]` shape copy the caller's array. A write through any of them changed an array's dimensions or strides without its size or buffer, so later reads went past the buffer; a read in a hot loop now allocates (hoist it, or use `shape[i]` / `NDim`), and new `params ReadOnlySpan<long>` overloads of `reshape` / `reshape_unsafe` / `resize` keep inline calls at one allocation. `Shape(long[] dims, char order = 'C', bool copy = true)` and `Shape(long[] dims, long[] strides, bool copy = true)` replace the two-parameter constructors (recompile: the old signatures are gone), and `copy: false`, NumPy's keyword passed by name, keeps an array nothing will write into again instead of copying it.
- `np.ndarray(shape, dtype, buffer, offset, strides, order)` is NumPy's `ndarray.__new__`: float64 and C order by default (they were float32 and `'F'`), `order` is honored and validated without a buffer, the buffer is any bytes-like `object` whose bytes are read as `dtype` (its element type was the dtype), `offset` and `strides` count bytes, and the fourth positional argument is `offset` (a `char` there is a compile error: name `order:`). The wrap constructors read a larger buffer's prefix and raise `TypeError` for a smaller one (both raised `ArgumentException`), and `flags.aligned` is false for misaligned memory (`np.frombuffer` / `getfield` at odd offsets too), so `setflags(align: true)` can raise and `np.require(..., 'A')` can copy; 167 of 185 probe cases match NumPy (21 did), gated by a 5,919-case `ndarray_ctor` tier.
- `np.var` / `np.std` / `np.nanvar` / `np.nanstd` / `np.mean` / `np.nanmean` return NumPy's dtypes, shapes and values for every loop: a 1-D-axis `nanvar` / `nanstd` is 0-d (it was `(1,)`), float16 / float32 inputs are summed in their own dtype (a float16 `nanmean` can overflow to `inf`), an integer or bool `mean` loop wraps, and a flat decimal mean is decimal (it was float64).
- `np.median` into an integer or bool `out=` stores NumPy's value, cast unsafely as NumPy's `mean(out=out)` does (`[1, 5, 9]` for `arange(12.).reshape(3, 4)` along axis 1; a nonzero median is True), and `np.ptp` of a float input into an integer out raises subtract's `TypeError: Cannot cast ufunc 'subtract' output from dtype('float64') to dtype('int64') with casting rule 'same_kind'` with the maxima already in the out (both raised np.copyto's `InvalidCastException`); integer `np.ptp` wraps in its dtype and widens exactly (`np.ptp(int8 [127, -128], out=int64)` is 255; it was -1).
- `np.float_power(x, 2.0)` is `pow`, no longer `x*x`; float16 `np.power` is `powf` (`-0.0 ** 0.5` is `+0.0` and `-inf ** 0.5` is `+inf`, as in NumPy); and a one-element operand with more dimensions than the other gives the broadcast shape in every binary ufunc (`(7,) + (1, 1)` is `(1, 7)`; it lost the leading axes).
- On C# 12, the default language of a `net8.0` project, `np.random.seed(null)` and `new PCG64(null)` no longer compile (`CS0121`; both compiled against 0.70.0): the overload that takes a `null` seed is chosen by `[OverloadResolutionPriority]`, which only C# 13 and later honor. Call `np.random.seed()` / `new PCG64()`, or set `<LangVersion>13</LangVersion>`; `net9.0` and later projects are not affected.
- A C# `string` is NumPy's `str`: the implicit `string` -> `NDArray` conversion and `np.array(string)` give a 0-d `U` array (the text was parsed as numbers; parse with `astype(np.float64)`), a `.npy` `<U1` loads as `U1` (it loaded as `Char`), and `np.@char` is the `numpy.char` module (it still converts to the char dtype).
- C# number literals are weak Python scalars: a float16 / float32 array compared with a `double` literal compares in its own precision, an out-of-range integer literal raises `OverflowException` in a binary ufunc and in every store (`a[0] = 1000` on int8, `np.full(3, -1, dtype: np.uint8)`, `np.copyto(int8, 1000)`; they wrapped), a NaN literal into an integer array raises, a `Complex` one into a real array `TypeError`, `'equiv'` refuses an integer into int32, and a 0-d array that is not a literal promotes as a NumPy scalar (`uint8 + int64[1]` is int64).
- NumPy's exception types: `AxisError` for an out-of-range axis, `IndexError` from `np.put` / `np.take` / `np.choose`, the indexers and `np.einsum_path` (an ellipsis without its operand, an explicit path past the operands), `TypeError` for a ufunc cast a casting rule refuses, a dtype string NumPy rejects, a numeric cast of a non-0-d array, `np.ediff1d`'s refused ends and a `null` stored into an integer array, `ValueError` from `np.nditer`'s construction errors and `np.nested_iters` without an operand, a zero slice step and `np.nonzero` of a 0-d array (they were `ArgumentException`, `IndexOutOfRangeException`, `ArgumentOutOfRangeException`, `NotSupportedException`, `InvalidOperationException` or `IncorrectShapeException`); `AxisError.ActualValue` is the axis as invariant text (`"-3"`; `AxisError.Axis` keeps the number).
- One NumPy signature: `np.sum` / `np.prod` / `np.mean` / `np.var` / `np.std` and the `max` / `min` family (and their `ndarray` methods) have one overload each in NumPy's order, so a positional third argument is `dtype` / `out` (name `keepdims:`); the generic `np.amax<T>` / `a.max<T>()` and `NDArray.amax` / `amin` are gone; `np.evaluate(expr, x)` passes `x` as an operand (name `@out:`).
- Each array class has one indexer, NumPy's `__getitem__` / `__setitem__`: `NDArray`'s other indexers bind `this[params object[]]` with the same results, an `int[]` key to `__getitem__` is an index array, and `NDArray<T>`'s indexer returns `NDArray<T>` (its typed scalar indexers are gone: `(double)a[0]`, or `a.GetValue<double>(0)` in a hot loop).
- `TensorEngine` subclasses implement the new abstract members that carry each computing function; `np.sum` / `np.mean` call `ReduceAdd` / `ReduceMean`; the LAPACK members (`Cholesky` ... `Svd`) are `DefaultLinalgEngine`'s kernels under `TensorEngine.Linalg`; `BackendFactory.GetEngine()` returns `TensorEngine.Default`, results and views bind the engine that made them, and a null array operand raises `ArgumentNullException` when the call starts.
- A fresh ufunc result takes NumPy's K-order layout (its strides and flags change for permuted, F-ordered and flipped operands), and `np.fft` keeps the input's memory order.
- The print options and `np.setbufsize` are context-local under Python 3.12's `ContextVar` rules: a new thread starts at the defaults, `Task.Run` and `await` continuations see the caller's.
- `NDScope.Dispose` on a thread other than the one that opened the scope throws `InvalidOperationException` in every build (only a Debug assert guarded it): a hand-written scope held across an `await` was reused on the continuation's thread, where its close freed the opening thread's later arrays. Close the scope before the `await` and open another after it, or mark the async method `[NDScopedAsync]`; a refused scope's arrays are left to the finalizer.
- Text I/O follows NumPy's encodings and CPython's formatter: `np.loadtxt(Stream)` / `np.savetxt(Stream)` default to Latin-1 (was UTF-8), a named file no longer detects a BOM, `encoding:` takes Python's codec names, `np.savetxt` / `ndarray.tofile` raise CPython's errors where they were lenient, and `np.fromstring` / `np.fromfile` read text as NumPy does.
- `a[true]` returns a copy (it was a view), and `(bool)` of a one-element array answers its truth value (it threw).
- Creation: `np.arange` raises NumPy's errors (a zero step `DivideByZeroException`, an out-of-range bound `OverflowException`; it wrapped), `np.asanyarray` of a C# object list reads integers as int64 and floats as float64, `np.where` / `np.select` read C# literals as Python scalars (`np.where(c, 7, 7)` is int64), and `np.frombuffer`'s range checks raise `ValueError`.
- `np.pad` reads its widths before its mode (a null mode is `ValueError`; one `int[]` entry per axis is refused, write an `int[,]`), a value that does not fit a view assignment or `np.insert` raises `ValueError` (was `IncorrectShapeException`), and `np.average` / `np.isin(assume_unique: true)` answer as NumPy does.
- `np.complex64` / `np.csingle` are scalar classes (`np.zeros(3, np.complex64)` no longer compiles), and `np.longdouble` / `np.clongdouble` / `np.intc` / `np.longlong` and their unsigned twins are classes of their own (equal to their twin, not the same object).
- `np.sort` / `np.argsort` validate `kind` and take `order` / `stable`, `np.argsort`'s first parameter is `a` (was `nd`), and `np.format_float_positional` / `np.format_float_scientific` take `object x` and a `string trim`.
- pythonnet: numpy's `<U1` imports as a `U1` view (was a `Char` copy), `np.bytes_` as a 0-d `S<n>`, and `FromNumpyDtypeStr` / `FromBufferFormat` return `DType`.
- `np.polyder` is NumPy's recursion: a 2-D `p` is differentiated along its first axis (`np.polyder(np.ones((3, 2)))` is `[[2, 1], [2, 1]]`; it raised), and a 0-d `p` raises `TypeError: len() of unsized object` at every order (`m = 0` returned it).
- `np.isscalar` answers as NumPy does: a `Type` is not a scalar (`np.isscalar(typeof(int))` was `True`), and `Half`, `BigInteger`, `Char8` and `DateTime64` are (they were `False`).
